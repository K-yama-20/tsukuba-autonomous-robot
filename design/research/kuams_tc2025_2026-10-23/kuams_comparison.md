## 1. 要点

KUAMS は、本走行で**選択課題を一つも実施せず（信号認識横断も「不実施」）、完走だけを狙って**、2200 m を 70 分でゴールした。平均は約 0.52 m/s である。

構成は、ほぼ標準の部品を組み合わせただけである（WHILL Model CR、Nav2、NDT による自己位置推定）。違いは「止まらない作り」と「waypoint ごとに動きを足せる仕組み」にある。

1. **自己位置推定が「推定不能」で止まらない**
   - NDT が収束しないときはその回の更新を捨て、車輪オドメトリによる推測だけで進み続ける
   - スコアが悪いときも警告を出すだけで、使い続ける
   - 自己位置推定から走行を止める道筋が、どこにもない
2. **Nav2 が失敗しても、同じ waypoint をすぐに送り直す**
   - Nav2 の行動木は、失敗するまでに回復動作（costmap の消去、回転、待機、後退）を6回試す
   - それでも失敗すると、waypoint の実行ノードが同じゴールを送り直す
   - 回数に上限はなく、人の操作も要らない
3. **waypoint ごとに「機能」を書ける**：CSV の各行の末尾に命令を並べる
   - `skip`：waypoint の上に物があれば、その waypoint を諦めて次へ進む
   - `wait:N`：N 秒待つ
   - `pause`：人の再開操作まで待つ
   - `lineup`：前が空くまで待ち、その後 Nav2 を使わずに waypoint へまっすぐ進む
4. **途中の waypoint から再開できる**（`start_id`）
5. **コースの事前公開を前提にした道具**
   - 試走で手動走行しながら waypoint を自動で記録する（waypoint_editor）
   - 経路沿いに見える点だけで地図を作り、区間に分ける（map_divider）
   - waypoint で地図と初期位置を切り替える（2025-10 の時点では骨組みだけ）
6. **速度と回転を低く抑えている**
   - 最大 0.8 m/s、旋回は最大 0.3 rad/s
   - collision_monitor で、前方 1.0 m の四角に点が入ると停止する。2 秒後に衝突しそうなら減速する

gouda の今の作りは、ほぼ逆向きである。推定不能になったときと Nav2 が失敗したときは、自動で一時停止に入り、再開には人の操作が要る（TR-07）。waypoint の `kind: stop` は記録に残るだけで、走行の動きは変わらない。人のこの方針の転換（DEC-304〜314、DEC-340〜346）は、KUAMS が実際にやっていたことにかなり近い。

## 2. 項目ごとの比較

### 2.1 車体とセンサ

| 項目 | KUAMS | gouda |
|---|---|---|
| 車体 | WHILL Model CR。ROS 2 ドライバ（kzm784/ros2_whill）で速度指令とオドメトリを扱う | 電動車椅子を ESP32 の DAC で操作する（firmware v4 は未投入） |
| オドメトリ | **車輪エンコーダ**（WHILL）。EKF は設定があるが、launch でコメントアウトされている | **車輪エンコーダなし**。GLIM の odometry-only（LiDAR + IMU）を使う |
| 自己位置推定用の LiDAR | URDF・launch では VLP-16（高さ 0.8 m）。README は Mid-360 と書いており、2025 年の構成ははっきりしない | XT-32 |
| 障害物用の LiDAR | Livox Mid-360（前方の高さ 0.3 m）の点群を、センサ高さ ±0.2 m の帯で 2D の LaserScan にする | XT-32 の点群を VoxelLayer と ObstacleLayer に入れる（MID-360 の追加を検討中） |
| GNSS | 使っていない | mosaic-G5 RTK（解が得られない件を調査中） |

**差の意味（推測を含む）**

- KUAMS は車輪オドメトリがあるので、LiDAR の照合が外れても推測航法で数秒から数十秒は進める
- gouda はオドメトリも LiDAR（GLIM）に頼っている。そのため、LiDAR の LAN が途切れる、人混みで点群が乱れる、といった事態で、オドメトリと照合の両方が同時に悪くなる（第127便の分析と同じ）
- 「推定不能でも止まらない」作りを gouda で真似するなら、車輪エンコーダ（DEC-292）の有無で、取れるリスクが変わる

### 2.2 自己位置推定

| 項目 | KUAMS（lidar_localization_ros2、確認） | gouda（ND-07、確認） |
|---|---|---|
| 方式 | ndt_omp。分解能 2.0 m、ボクセル 0.2 m、スキャン 1〜100 m、反復 35 回 | Autoware 系の NDT scan matcher と EKF localizer。GLIM のオドメトリを入力にする |
| 初期化 | パラメータか RViz で初期姿勢を与える。探索はしない | 人の初期姿勢をもとに、ndt_align_srv（モンテカルロ探索）、EKF の初期化、trigger の順に進める |
| 照合が収束しないとき | **その回の更新を捨てて return するだけ**。前回の姿勢に車輪オドメトリの速度を積分したものを使い続ける | 状態が「推定不能」になり、map→odom を出さなくなる。モードは TR-07 で一時停止に入る |
| スコアが悪いとき（しきい値 2.0 超え） | **警告のログを出すだけで、結果は採用する** | EKF の標準偏差が PRM-92（0.5 m、実測値ではない）を超えると推定不能になる（第123便で実際に起きた） |
| 出力 | `enable_map_odom_tf: true` で map→odom の TF を出す | map→odom を ND-07 だけが出す |
| 独自の変更 | 姿勢とスコアを CSV に記録する機能（研究用）。初期姿勢の前にオドメトリが来ると落ちる不具合の修正 | ― |

この行で言えることは次のとおり。

- gouda は、2026-10-22 の実車での開始4回のうち、少なくとも2回を推定不能による一時停止で止めている（第121便・第123便）。KUAMS の作りなら、どちらの場面も止まらない
- その代わり、本当に位置を見失ったときも走り続ける。1.5 節が禁じる「推定が誤っているのに走る」状態を、KUAMS は受け入れている
- KUAMS は 2025 年にゴールまで走ったので、この割り切りはつくばのコースでは結果的に通用した。ただし、走行中に推定がどれだけずれたかの記録は公開されていない

### 2.3 Nav2 の設定（KUAMS は `params_nav2.yaml` を確認）

| 項目 | KUAMS | gouda |
|---|---|---|
| ゴールの送り方 | **waypoint を1つずつ NavigateToPose で送る** | 全 waypoint を NavigateThroughPoses でまとめて送る（RemovePassedGoals は 0.7 m） |
| controller | **MPPI**：vx_max 0.8、wz_max 0.3、PreferForward、PathAlign の重み 14 | Regulated Pure Pursuit：desired 1.25 m/s、回転 1.0 rad/s |
| planner | NavFn（A*）、allow_unknown、SimpleSmoother で平滑化 | NavFn（テンプレートのまま）。smoother_server は残している |
| 経路の引き直し | 1 Hz | 1 Hz（PRM-103。第141便で上流の 0.333 Hz から変更） |
| 回復動作 | RecoveryNode 6 回（costmap の消去 → 1.57 rad の回転 → 5 秒の待機 → 0.3 m の後退） | 上流の BT のまま。外側の回数 PRM-18 は 9999999 |
| goal checker | xy 0.5 m、yaw 1.0 rad、stateful | テンプレートのまま |
| progress checker | 5 秒で 0.5 m 動かなければ失敗 | テンプレートのまま |
| local costmap | odom 基準、8×8 m、**static layer なし**。障害物は Mid-360 の LaserScan だけ。inflation 1.0 m | VoxelLayer（XT-32）。高さ −0.065〜1.185 m。inflation は PRM-72 の 1.0 m |
| global costmap | static（pcd2pgm の地図）と obstacle と inflation 0.5 m。**障害物は 2.5 m 以内だけを書き込み、3.0 m まで消去する** | static、ObstacleLayer、KeepoutFilter、SpeedFilter、inflation |
| collision_monitor | **あり**。前方 1.0 m × 幅 0.6 m の四角で停止（`max_points: 3`。Humble の定義では、4点目から動作する）。footprint で 2 秒先の衝突を予測して減速 | **外している**（RQ-I072） |
| 速度の上限 | velocity_smoother で 0.8 m/s。後退 −0.5 m/s | 1.25 m/s。区間ごとの SpeedFilter（速度マスク）がある |

この表から読めること（推測を含む）は次のとおり。

- **1つずつ送る方式**
  - waypoint ごとに Nav2 の結果が返るので、「失敗したらその waypoint をもう一度」「物があれば次へ」「この waypoint の後で待つ」を、BT をいじらずに waypoint の実行ノードの側で書ける
  - gouda の一括送信では、失敗が1つでもあると、ミッション全体の失敗（TR-07）になる
- **回転を遅くしている**
  - wz_max は 0.3 rad/s。その場で回るときに点群や推定が乱れるのを避けるためと思われる
  - 回転が遅いと、NDT の初期値が大きく外れにくい
- **global costmap の障害物の範囲が短い**
  - 遠くの人やロボットが global の経路を塞がない
  - 地図にない物（屋台・コーン）は近づいてから避ける
  - これは DEC-348（遠くから認識して、近づくにつれて更新する）とは逆向きである
- **local に static layer がない**
  - 自己位置がずれても、地図の壁が local でずれて現れることがない
  - local の回避は、そのとき見えている物だけで決まる

### 2.4 waypoint の実行と、waypoint ごとの機能（kzm784/waypoint_manager、確認）

waypoint の CSV の形式：`id, x, y, z, qx, qy, qz, qw, 命令1, 命令2, ...`。命令は `skip:2`、`wait:2`、`pause` のように書く。

| 命令 | いつ動くか | 動作（コードで確認） | つくばで使う場面（推測） |
|---|---|---|---|
| `skip` | waypoint へ出発するとき | waypoint から 2.5 m 以内に来たとき、waypoint の 2.5 m 以内に LaserScan の点が5つ以上あれば、Nav2 を取り消して次の waypoint へ進む | waypoint の上に人・他のロボット・コーンがいて、たどり着けない。たどり着けないゴールで回復動作を繰り返し、滞留で失敗するのを防ぐ |
| `wait:N` | waypoint に着いたとき | N 秒待ってから次へ進む | 横断歩道の前で一度止まる、信号の前で減速して待つ |
| `pause` | waypoint に着いたとき | `/pause_end`（RViz のボタン「PauseEndTool」）が来るまで待つ | 停止線で止まり、人の確認で横断を始める（gouda の DEC-343 と同じ考え方） |
| `lineup` | waypoint へ出発するとき | 前方の幅 ±0.5 m・奥行き 2.0 m にある点が2つ未満の状態が、6回続けて届くまで待つ。その後は Nav2 を使わず、0.2 m/s で、向きを P 制御しながら waypoint へまっすぐ進む。0.3 m まで近づいたら終了 | 列に並んで順番を待つ場面や、狭い所。2025-10-14 に追加され、既定の launch には入っていない。本走行で使ったかは分からない |
| ABORTED（命令ではない） | Nav2 が失敗したとき | **同じ waypoint をそのまま送り直す**（上限なし） | 一時的な塞がりで止まっても、待てば進む |
| `start_id` | 起動するとき | 指定した waypoint から始める | 途中で手動に戻した後に、続きから再開する |

この仕組みは、命令ごとに独立したサーバ（skip_server など）を後から足せる形になっている。

- 2025-10 に `lineup` と `map_change`（地図の切り替え）を足している
- `map_change` の中身は、本走行の時点の公開版ではまだ空である（地図と初期姿勢の YAML を読むところまで）

gouda との差

- gouda の `kind: stop` は、まだ記録に残るだけである。第140便で「区切りごとに goal を出し、人の『横断を始める』操作で次へ進む」を提案しているが、承認待ちで実装はない
- KUAMS は `pause` と `wait` だけで、同じことを1年前に実現していた
- 「物があれば waypoint を飛ばす」機能は、gouda にない
  - 第140便の DEC-344 に「waypoint を飛ばす段の制限」があるが、飛ばす条件（waypoint の上に点がある）までは設計されていない
  - KUAMS の条件は単純で、点の数と距離の2つだけである

### 2.5 地図と waypoint を作る道具（コースの事前公開を前提にしたもの）

| 道具 | 内容（確認） | gouda の対応 |
|---|---|---|
| waypoint_editor | RViz で 2D・3D の地図を見ながら waypoint を置く。2025-11 に、自己位置の topic から一定間隔で自動で記録する機能、戻る・進む、直前の waypoint からの距離表示を追加した（本走行の直前） | monitor の waypoint タブ（手で置く）。走りながら自動で記録する機能はない |
| pcd2pgm | PCD の地面を PMF で取り出し、残りの点の高さを近くの地面の点（12点）から測る。0.10〜1.50 m の点を障害物として 2D 地図にする | map_convert（地面からの高さ。DEC-093） |
| map_divider | waypoint を 1 m 間隔に補間し、各地点から octomap で見通せる点だけを集め、15 m ごとに PCD を分けて保存する | なし（地図は1枚） |
| opc_ros2 ほか | 10〜30 m の格子ごとに「その格子から見える点」をブルームフィルタで記録しておき、走行中は今いる格子から見える点だけを NDT の地図として出す。広い地図や、木・建物の裏側による誤照合を減らす研究 | なし |
| waypoint_function_map_change_server | waypoint の命令で 2D 地図、3D 地図、初期姿勢を切り替える。中身は未完成 | なし |

**つくば向けの読み方（推測）**

- コースは事前に公開され、試走会で走れる。そこで、試走で手動で走りながら、地図用の点群と、同じ経路に沿った waypoint（自動記録）を同時に作る、という使い方に向いた道具がそろっている
- 地図を「経路から見える点だけ」に絞る研究（map_divider と opc）は、つくばのような長いコース（2.2 km 超）で、NDT が遠くの物や反対側の物に引っ張られるのを防ぐ考え方である
- ただし、本走行でこれを使ったという証拠は、コードにはない。opc_ros2 の設定のパスは `robomech_ws`（論文用）で、研究室の構内の地図だった

## 3. gouda に取り入れられそうなこと

取り入れるかどうかは承認事項（1.2）であり、ここでは何も実装していない。安全に関わるものは、1.5 の禁止事項（推定不能の扱い、PC 出力を中立にしただけで停止とみなすこと）と関係する。

| # | KUAMS のやり方 | gouda の関連 | 案（どれも人の判断待ち） |
|---|---|---|---|
| 1 | 推定不能で止まらず、オドメトリの推測で進み続ける | DEC-306、DEC-340、DEC-342（推定不能の扱い）、DEC-292（エンコーダ） | gouda は推測を支える車輪エンコーダがないため、そのままは真似できない。DEC-342 の「少し進んでから待つ」の進める距離・時間を、オドメトリの質で決める必要がある（実測） |
| 2 | Nav2 が失敗したら、同じ waypoint を送り直す。上限なし | DEC-307、TR-07 | waypoint を1つずつ（または区間ごとに）送る方式にすると、失敗した区間だけを繰り返せる。第140便の「区切りごとに goal を出す」と整合する |
| 3 | `skip`：waypoint の上に物があれば次へ | DEC-344 | 判定は「waypoint から r 以内に点が N 個以上」と単純にできる。r と N は実測で決める |
| 4 | `pause` と `wait` を waypoint の属性にする | DEC-343（横断歩道）、`kind: stop` | KUAMS の `pause` は、RViz のボタン1つで再開する。DEC-345 の規則（PC のボタンで再開してよいか）が決まれば、同じ形にできる |
| 5 | `start_id`：途中の waypoint から再開 | TR-10（残りの waypoint で再開） | gouda にもある。KUAMS は起動の引数で指定する |
| 6 | 回転を遅く（0.3 rad/s）、直進を 0.8 m/s に | PRM-17 など（1.25 m/s、1.0 rad/s） | 推定が乱れる原因を減らす。値は実測の項目にする |
| 7 | collision_monitor（前方 1 m で停止、2 秒先の衝突で減速） | RQ-I072（外した）、TRB-001、TRB-002 | コーンや歩行者への接触は失敗になる（DEC-339）。外した理由と照らし合わせて見直す |
| 8 | global には 2.5 m 以内の障害物だけを書き込む | DEC-348 | 遠くの人が経路を塞ぐ問題と、近づいてからの回避のどちらを重く見るか |
| 9 | 試走で走りながら waypoint を自動で記録する | waypoint タブ | 地図作成の走行の軌跡（GLIM の trajectory）から waypoint の候補を作る道具は、提案にできる |

## 4. 分からないこと

- KUAMS の本走行での設定は分からない。公開されているのは 2025-10-03 以前の `kuams` と 2025-10-14 以前の `waypoint_manager` で、つくばの地図・waypoint の CSV・どの命令をどこに置いたかは公開されていない
- 自己位置推定に VLP-16 と Mid-360 のどちらを使ったかは、コードからは確定できない（launch は `/velodyne_points` を使い、README は Mid-360 と書いている）
- 走行中のトラブル、試走での失敗、教訓は、文章のどこにも見つからなかった
  - 載っていそうなのはチームの参加レポート（report_2564.pdf）とシンポジウムの発表だが、どちらも読めていない（5 章）

## 5. 文献と公式記録から分かったこと

### 5.1 本走行の記録（スプレッドシートを私が確認）

- KUAMS は 11:30 に出走し、12:40 にゴールした。走行時間 70 分、2200 m で、マイルストーンは3つとも達成している
- **選択課題（事前計測なしエリアの通過、信号認識横断、チェックポイント通過と経路封鎖の迂回、集荷・配達）は、5つともすべて「不実施」だった**
- 課題を達成しなかった理由は、これで説明がつく。達成には「完走」と「選択課題2つ以上」が要るからである
- 比べると、他の完走チームはどれも、少なくとも信号認識横断を「実施・成功」にしていた
  - 宇都宮F（UNITE）
  - 芝浦工大（Voyager）
  - 筑波大 Kerberos（チェックポイントも成功し、課題を達成）
- 平均速度は約 0.52 m/s で、停止を含む（エージェントの計算。完走チームで最も遅い）。設定の最大 0.8 m/s と合っている

**解釈（推測）**

- KUAMS は課題を捨て、「遅くても止まらずに完走する」ことに絞ったように見える
  - 2.4 節の `pause` と `wait` は、課題の採点のためではなく、横断を安全に通るためだった可能性がある
- gouda の intent の優先順位「0. 本番で完走できる」（必達 2.2 km）と、同じ方針である
- 方針が同じなので、KUAMS の作りは gouda の参考として特に向いている

### 5.3 研究の論文（2本とも、八木・前の両氏が著者であることを、私がページで確認した。内容はエージェントが本文から読んだもの）

[JRM Vol.37 No.6 p.1355（2025）](https://www.fujipress.jp/jrm/rb/robot003700061355/)

- 予定経路の waypoint を 0.5 m 間隔に補間し、各地点から見える点だけを残した「観測可能点群地図」を作る
  - 範囲は 50 m、上下 ±30°。OctoMap の 0.2 m 格子で、隠れた点を除く
- 経路 10 m ごとに地図を分け、境目の waypoint で次の地図に切り替える
- 元の地図は GLIM で作り、waypoint は手で約 1.0 m 間隔に置いた
- これは map_divider と map_change_server に当たる

[JRM Vol.38 No.4 p.1073（2026）](https://www.fujipress.jp/jrm/rb/robot003800041073/)

- 経路ではなく、一様な格子（10・20・30 m）ごとに、地面の点に置いた仮想の視点から Hidden Point Removal で見える点を求める
- これは opc_ros2 に当たる

どちらの論文も、実験は関西大学の構内で行っている。つくばのコースで使ったという記述はない。

### 5.4 ROBOMECH2025 2A2-R12「機能的ウェイポイントを利用した自動ドアの通過」（要旨のみ）

- waypoint に「その場所で要る動作」を持たせる考え方である。2.4 節の waypoint_function_server に当たる
- 要旨は、RGB-D で自動ドアを認識して通過する例を挙げている
- つくばでは、同じ仕組みで pause・wait・skip を使ったと考えられる（推測）
