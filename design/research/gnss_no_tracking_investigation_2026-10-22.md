## 3. 原因の候補の切り分け

### 3.1 Gouda のプログラム（ドライバの設定、中継）— 証拠から外れる

| 候補 | 判断 | 根拠 |
|---|---|---|
| ドライバの設定（gnss_config の差し込み） | 外れる | Gouda が変える項目（device、configure_rx、frame、receiver_type gnss、multi_antenna、use_gnss_time false、publish、rtk_settings.serial_1.port）は、衛星の追尾（信号・衛星系・高度角のマスク・アンテナの給電）に触れない。10-19 に衛星を捕まえた起動と、10-20 の観測 0 の起動は、同じ設定（serial_1 はまだ無い） |
| `sto, 90, 0`（/config の取付から） | 外れる | 方位の出力のオフセットだけ。追尾に関係しない |
| NTRIP の中継・rtk_settings.serial_1 | 外れる | 10-20 の時点で gnss_rtk.yaml は無く、中継は起動していない（起動のログ「not found」）。それでも観測 0 |
| 起動のたびの `sntp, on` の拒否 | 外れる | 10-19 の衛星を捕まえた起動でも同じ拒否が出ていた |

Gouda のコードが衛星の追尾を止めている証拠は見つからない。

### 3.2 受信機の設定の変更（AI が行った DualAnt）— 最も疑わしい

- Hardware Manual（v1.1.1 §4.2.3.2）は DualAnt の条件として、前置増幅（アンテナの利得 − ケーブルの損失）が全帯域で 35 dB 未満（AGC 30〜50 dB）、2 本の差 5 dB 以内、必要なら減衰器、を求める。**AI はこの条件を確かめずに DualAnt を勧めた**（アンテナの利得は「原本未照合」と書いたまま進めた）。人の判断「アンテナは動作確認済み品をレンタルしているから、調べる必要ない」は、アンテナが壊れていないことの確認で、利得の条件の確認ではない。
- 推測（未確認）: 利得が条件を超えると、DualAnt の前段が飽和し、主アンテナも含めて信号を捕まえられない可能性がある。
- 推測（未確認）: アンテナの給電は 2 本で合計 150 mA まで、過電流なら**両方の給電が切れる**（Hardware Manual §4.2）。2 本の消費の合計が多いと、両方とも給電なしになる。ただし 10-19 は同じ 2 本がつながったまま主アンテナで衛星を捕まえていたので、アンテナ・ケーブルが変わっていなければ、この候補は弱い。

### 3.3 ハードウェアの変化 — 人の確認が要る

- 10-19 の後に、アンテナ・ケーブル・分配器などを替えたか（人の確認）。替えていれば 3.2 と別の原因がありうる。

## 4. 受信機をつないで行う確かめ（承認事項）

1. **試験 T1（読むだけ、DEC-299）**: 受信機を VM につなぎ、Gouda は止めたまま（mode を先に確かめる）、受信機の電源を入れ直す（USB の付け直し）。Boot に保存されたドライバのストリームが USB1 に SBF を出す（推測。出なければその事実を記録）。USB1 を MRTKLIB の `mrtk relay` で 60 秒ほど生のまま記録する（コマンドは送らない）。ReceiverStatus から AGC（前段ごと）と RxError（アンテナの過電流など）、MeasEpoch の観測の数を読む。場所は 10-19 に衛星を捕まえた屋内の同じ所か、屋外。
2. **試験 T2（受信機の設定の変更、DEC-300）**: frontend mode を元の Nominal に戻す（`sfm, Nominal` → `eccf, Current, Boot` → `exeResetReceiver, Hard, none`、USB2）。衛星を捕まえるようになれば、DualAnt が原因と決まる。そのときは、方位のために減衰器などで条件を満たすか、方位をあきらめるかを人が決める。
3. **試験 T3（caster への接続だけ、DEC-301）**: 第114便では中継の入力が「待機」のまま 0 バイトだった（衛星の問題と別に、caster につながっていない）。gnss_rtk.yaml を読んで caster に NTRIP の要求を 1 回送り、応答の**状態の種類だけ**（接続できない・HTTP の状態の番号など）を出す小さな確かめ（値は出さない）。Point One が NTRIP v1 を受け付けるかがここで分かる。DEC-298（v1・TLS なし）の回答が前提。

## 5. プログラムの改善（今回の調べで見えたもの。DEC-302）

- **monitor が「衛星 0」を示さない**: 今は navsatfix が無いと「NOT_RECEIVED」になるだけで、受信機が信号を 1 つも捕まえていない（MeasEpoch n 0）のか、測位できないだけなのかが分からない。MeasEpoch の観測の数と受信機の時刻の有無を出す。
- **中継の失敗の理由が見えない**: 秘密を出さないため str2str の msg の欄を全部捨てている（DEC-156）。そのため第114便で、caster に「つながらない」のか「拒否された」のかが分からなかった。msg を、秘密を含まない種類（connect error の番号、timeout、disconnected、HTTP の状態の番号）に分類して記録する。
- **2 つ目の「Invalid command」**: 第114便で起動のときに 2 回出た（1 回は sntp。もう 1 回は serial_1 の設定のコマンドと推測、未確認）。ドライバは秘密を持たないので、応答の文は読んでよい。次の起動で確かめる。
- **AGC・アンテナの給電の状態が ROS に出ない**: このドライバは ReceiverStatus の message を持たない（VM の interface の一覧で確認）。DEC-297 の記録の追加では足りず、受信機の状態を別に読む手段が要る（T1 の方法を道具にする案）。

## 6. AI の仮定の点検（人の問いへの答え）

確かめずに置いた仮定（今回の件に関わるもの）:
1. DualAnt の条件（アンテナの利得・2 本の差・給電の電流）を満たしていると仮定して、DualAnt を勧めた（§3.2）。
2. 2026-10-20 の観測 0 を「屋内だから」と仮定した（§2）。
3. Point One が NTRIP v1・TLS なしで受け付けると仮定して中継を作った（DEC-298 で問うているが、確かめはまだ）。
4. 中継の msg を全部捨てても、状態の文字で足りると仮定した（§5。足りなかった）。
5. 状態の表示（monitor の GNSS の欄）で「受信なし」が分かれば足りると仮定した（§5。衛星 0 を区別できなかった）。

コードの中で、未確定の値を推測で埋めている箇所は見つからなかった（gnss_config の差し込みは承認済みの PRM と設計の決定だけ。雛形の値は変えない）。
