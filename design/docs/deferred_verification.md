## VL-01 PC がシリアルを開くと ESP32 がリセットされるか

- 人の指示（分岐セッションからの転送、2026-10-21）：「これの優先事項は低いが、試験する価値は高いと考える。後で検証する項目に追加してくれないか？適切な保存先が現在存在していないのなら、新たに保存先の文書を作っても良い。」
- 問い：vehicle_bridge が pyserial で ESP32 のシリアルを開いたとき、ESP32 がリセットされるか、書き込み（boot）モードに入るか。
- なぜ大事か：USB の差し直しの後の再接続（提案。作業記録 `reports/worklog/2026-10-21_rev110_dr15_scan_usb_uptime.md` §3、実装していない、人の許可待ち）では、vehicle_bridge がポートを開き直す。開くたびにリセットされると、firmware の起動中は DAC に書かない時間ができ、設定（NVS）・起動の記録の扱いも変わる。
- 机上で分かっていること（分岐セッションの調査。記録した側は該当の行を読み直していない。旧 bridge の行だけは確かめた）：
  - 事実：VM の pyserial 3.5 は DTR=True・RTS=True が既定（`/usr/lib/python3/dist-packages/serial/serialutil.py:216-217`、`serialposix.py:335-338`）で、os.open の後に DTR、次に RTS を設定する。
  - 事実：旧 bridge（`gouda_vehicle/gouda_vehicle/hardware_bridge.py`）は、開く前に `dtr = False`・`rts = False` にしていた（記録した側で確認）。そのコメントは「ドライバが開くときにパルスを出すことがある」。`firmware/gouda_esp32_v4/platformio.ini` も `monitor_dtr = 0`・`monitor_rts = 0`。新しい `gouda_core/gouda_core/vehicle_bridge_node.py` はどちらも設定していない。
  - 推測：Linux は開いたときに DTR と RTS を同時に有効にする（一般的なカーネルの振る舞い。ソースは読んでいない）。DevKitC の自動リセットの回路は、DTR と RTS の片方だけが有効なときにリセットまたは書き込みモードになるので、今のコードではリセットされない可能性が高い。
- 確かめていないこと：
  - 実物の基板の版と、EN の RC（図面と照合していない）。
  - cp210x のドライバが 2 本の線を同時に切り替えるか（VM のカーネルのソースは読んでいない）。
  - Parallels の USB の受け渡しが、線の切り替えを余分に起こすか。
- 試験の手順（ESP32 だけ、車両なし、約 5 分）：
  1. ESP32 を VM につなぎ、しばらく待つ。
  2. vehicle_bridge と同じ設定でポートを開き、最初の STATUS の `uptime_ms` を読む。リセットがなければ差し込んでからの時間、リセットされれば 0 に近い。開くのを何回か繰り返す。
  3. 旧 bridge と同じく、開く前に DTR・RTS を False にして繰り返す。
- `uptime_ms` が使える根拠：STATUS を作った時刻（`firmware/gouda_esp32_v4/include/gouda_v4/control.hpp` の sendStatus。`main.cpp` は loop の先頭で `millis()` を 1 回読む）。分岐セッションがコードで確かめた。
- 関係する記録：第77便の作業記録 §3（USB の差し直しの改善案）、DEC-050（実機照合）。
- 結果：未検証。

## VL-02 斜めに倒し切ったときの 1 mV の非対称が、実車の走行に影響するか

- 人の回答（分岐セッションからの転記、DEC-186）：「B4: さしあたっては案Aを採用し、保留とする。これは後の試験事項としてしかるべき文書に保存せよ。どの文書に保存したか報告せよ。」（案 A＝直さない）
- 問い：斜めに倒し切ったとき、x と y の出力に 1 mV の差が出る。これが実車の走行に影響するか（直進からのずれ、左右の差）。
- なぜ大事か：firmware を直すと、書き換えと卓上の試験（TS-17〜19）のやり直しが要る。直すかどうかを、実車の結果で決める。
- 机上で分かっていること：
  - 事実：firmware の mapVoltage（`firmware/gouda_esp32_v4/include/gouda_v4/control.hpp:31-46`）と Python の模型の map_voltage（`gouda_core/gouda_core/esp32_sim.py:53-68`）は同じ処理をする。円の外に出た出力を、1 mV ずつ円の内へ寄せる。|dx|＝|dy| のときは x だけを動かす。
  - 事実：承認値（中立 2500、最小 280、最大 4720 mV。PRM-43〜45）での出力を、模型で計算した（第88便）。(1,1)→(4069, 4070)、(1,−1)→(4069, 930)、(−1,1)→(931, 4070)、(−1,−1)→(931, 930)。どの向きでも、中立からの振れ幅は x が 1569 mV、y が 1570 mV で、x の方が 1 mV 小さい。旧 firmware の値（230／4700 mV）では差が出なかった（第71便）。
  - 事実：今の試験（`gouda_core/test/test_vehicle_core.py` の test_voltage_mapping_matches_previous_firmware_table）は、旧 firmware の値で x＝y を確かめている。承認値での非対称は試験していない。
  - 推測：1 mV は中立から端まで（2220 mV）の約 0.05%。車椅子側の deadzone や個体差に埋もれる大きさと考える（測っていない）。
- 確かめていないこと：実車での左右の速度の差。EMC-270 の入力の分解能。
- 試験の手順の案：
  1. 卓上：(1,1)・(1,−1)・(−1,1)・(−1,−1) に倒し切り、DAC の出力を測る（STATUS の target_x_mv・target_y_mv と、テスタでの実測）。
  2. 実車：斜めに倒し切ったときの軌跡の左右の差を見る。
  3. DEC-050・TS-17〜19 と同じ機会に行う。
- 直す場合の案：|dx|＝|dy| のとき、x と y を同じだけ寄せる（firmware と模型の両方）。次に firmware を書き換える機会にまとめる。
- 試験の追加（第89便、人の許可 DEC-191「VL-02 の試験（承認値で斜めの出力の x と y の差が 1 mV 以内であることを確かめる）を追加してよい。」）：斜めの 4 方向で、中立からの x の振れ幅と y の振れ幅の差が 1 mV 以内であることを確かめる。`gouda_core/test/test_vehicle_core.py` の test_diagonal_deflection_is_symmetric_within_1_mv（Python の模型）と、`firmware/gouda_esp32_v4/test/host/test_core.cpp` の VL-02 の節（firmware の中核）。今の出力は合格し、差が 2 mV に広がると不合格になることを、書き換えた写しで確かめた。この試験は机上の確認で、実車への影響の検証（この項目の問い）は済んでいない。
- 関係する記録：第71便の作業記録（`reports/worklog/2026-10-21_rev104_a9_a10_dec078_163_prm10.md`）、DEC-186、DEC-050。
- 結果：未検証。
