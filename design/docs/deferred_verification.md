## VL-01 PC がシリアルを開くと ESP32 がリセットされるか

- 人の指示（分岐セッションからの転送、2026-10-21）：「これの優先事項は低いが、試験する価値は高いと考える。後で検証する項目に追加してくれないか？適切な保存先が現在存在していないのなら、新たに保存先の文書を作っても良い。」
- 問い：vehicle_bridge が pyserial で ESP32 のシリアルを開いたとき、ESP32 がリセットされるか、書き込み（boot）モードに入るか。
- なぜ大事か：USB の差し直しの後の再接続（提案。作業記録 `reports/worklog/2026-10-21_rev110_dr15_scan_usb_uptime.md` §3、実装していない、人の許可待ち）では、vehicle_bridge がポートを開き直す。開くたびにリセットされると、firmware の起動中は DAC に書かない時間ができ、設定（NVS）・起動の記録の扱いも変わる。
- 机上で分かっていること（分岐セッションの調査。記録した側は該当の行を読み直していない。旧 bridge の行だけは確かめた）：
  - 事実：VM の pyserial 3.5 は DTR=True・RTS=True が既定（`/usr/lib/python3/dist-packages/serial/serialutil.py:216-217`、`serialposix.py:335-338`）で、os.open の後に DTR、次に RTS を設定する。
  - 事実：旧 bridge（`gouda_vehicle/gouda_vehicle/hardware_bridge.py`）は、開く前に `dtr = False`・`rts = False` にしていた（記録した側で確認）。そのコメントは「ドライバが開くときにパルスを出すことがある」。`firmware/gouda_esp32_v4/platformio.ini` も `monitor_dtr = 0`・`monitor_rts = 0`。新しい `gouda_core/gouda_core/vehicle_bridge_node.py` はどちらも設定していない。
  - 推測：Linux は開いたときに DTR と RTS を同時に有効にする（一般的なカーネルの振る舞い。ソースは読んでいない）。DevKitC の自動リセットの回路は、DTR と RTS の片方だけが有効なときにリセットまたは書き込みモードになるので、今のコードではリセットされない可能性が高い。
- 確かめていないこと：
  - 実物の基板の版と、EN の RC（図面と照合していない）。
  - cp210x のドライバが 2 本の線を同時に切り替えるか（VM のカーネルのソースは読んでいない）。
  - Parallels の USB の受け渡しが、線の切り替えを余分に起こすか。
- 試験の手順（ESP32 だけ、車両なし、約 5 分）：
  1. ESP32 を VM につなぎ、しばらく待つ。
  2. vehicle_bridge と同じ設定でポートを開き、最初の STATUS の `uptime_ms` を読む。リセットがなければ差し込んでからの時間、リセットされれば 0 に近い。開くのを何回か繰り返す。
  3. 旧 bridge と同じく、開く前に DTR・RTS を False にして繰り返す。
- `uptime_ms` が使える根拠：STATUS を作った時刻（`firmware/gouda_esp32_v4/include/gouda_v4/control.hpp` の sendStatus。`main.cpp` は loop の先頭で `millis()` を 1 回読む）。分岐セッションがコードで確かめた。
- 関係する記録：第77便の作業記録 §3（USB の差し直しの改善案）、DEC-050（実機照合）。
- 結果：未検証。
