## 1. 問い

信号あり横断歩道で、gouda は DEC-343 の横断歩道の状態遷移に「待機列」の動き（前が塞がっていれば待ち、空いたら追い越さずに進み、停止線で自律的に止まる）を足すべきか、それとも手動・手押しで横断して待機列の免除（TK-70）を使うべきか。

## 2. gouda の現状

- 【事実】waypoint の `kind` は `pass | stop` を持つが、記録に残すだけで振る舞いには使っていない（`gouda_core/gouda_core/waypoints.py:43`）。
- 【事実】NavigateThroughPoses の goal 1 つに、残りの waypoint を全部入れて送っている（`autonomy_client.py:272-289`、`autonomy_core.py:125-127`）。停止線で止まる仕組みも、待機列の仕組みもない。
- 【事実】Nav2 は RPP＋NavFn。collision_monitor は動かしていない（`nav2_config.py:5-8`）。recovery の spin・backup・wait は残している（同 8 行）。footprint は前 0.55 m・後 0.24 m・幅 0.60 m（PRM-69）、inflation 1.0 m（PRM-72）、最高速度 1.25 m/s（PRM-66）（`design/generated/params/gouda_nav2.yaml:7-13`）。goal の判定は上流の雛形の xy 0.25 m・向き 0.25 rad（`design/research/upstream_jazzy/nav2_bringup/params/nav2_params.yaml:92-96`）。
- 【事実】pending の DEC-343（model.yaml:61443）：`kind: stop` までの区切りごとに goal を出し、成功したら自律走行モードのまま段階 `rule_stop_hold` で止まり、人の「横断を始める」操作で次の区切りを出す。待機列のことは書いていない。提案書 §4（state_transition_redesign §4）も同じで、「止まっている間に後ろから人・ロボットが来ても動かない」までしか扱っていない。
- 【事実】DEC-345（model.yaml:61487、人の回答の原文）「異常の時にチームメンバーがボタンを押すなどの操作を加えると、走行失敗になる。再開ボタンを押しても良いのは一時停止線で停止した後や、信号が青になった後のみである。停止線での再開にpcのボタンを使って良いと考えられる。」
  → 待機列の中で「前が空いたら人がボタンで少し進める」形は、この回答では許されない。列の中の前進は自律でなければならない。
- 【事実】DEC-332（人の決定）は「waypoint の属性で止まり、人が再開ボタンを押して再開する形」。DEC-339 は確認走行区間の 3 分滞留・コース接触・歩行者衝突が失敗。DEC-304 は完走が必達。
- 【事実】DEC-343・345 の note には「AI は規則の原文を読んでいない（原本未照合）」とあるが、`regulations_2026.md` は本文を原本照合済としている。台帳の note が古い（記録の不整合。直すかは別便）。
- 【事実】移行元の Excel にはモジュール M-029 `gouda_crosswalk_controller_for_tc2026`「待機列への進入、停止線での停止、オペレータ再開、道路端での停止、横断開始条件の判定、横断完了までの状態遷移を管理」があり、状態は未決・「今回起動しない」（model.yaml:2422-2430、SRC-X01-0031）。待機列は元の設計の範囲に入っていた。

## 3. 規則の読み（原文照合済の転記から）と、KUAMS がしていたこと

### 3.1 規則

- 【事実】TK-66（regulations_2026.md:138）「自律走行で横断するすべてのロボットは、横断歩道手前の停止線を先頭に、待機列に一列に並ぶこと」。
- 【事実】TK-67（139）停止線では手前 1 m〜奥 0.5 m で自律的に一時停止。TK-23（58）帯の中に車体の一部、どの部位も奥 0.5 m を越えない。
- 【事実】TK-68（140）先頭は委員の指示でオペレータ操作により再開し、道路端の手前 1.5 m 以内で再び自律的に一時停止。TK-24（60）どの部位も道路端を越えない。
- 【事実】TK-69（141）後続は追い越さず一列で待機、前のスペースが空いたら前進。TK-65（130）列の白線はない、なるべく車道側に寄る。
- 【事実】EV-25（317）待機列で前のスペースが空いているのに 90 秒以上停滞（目安 1 m 前進しない）は走行失敗。
- 【事実】TK-70（142）「データ取得や単なる移動などのためにマニュアル走行や手押し走行で横断する場合は、待機列に並ばずに進んでもよい」。
- 【事実】選択課題B を実施しない場合（TK-77、161）「オペレータが、歩行者用信号機が青かつ横断歩道上に車両がいないことを判断し、オペレータ操作により走行開始して横断すること」。TK-78（162）横断可能な状況の 2 回目以内。
- 【事実】EV-19（306）スタートラインを越えたあと、チームメンバーが意図的にロボットに触れたり操作を加えた場合は失敗（一時停止から走行再開するための操作と、申告済みのバッテリー交換は除く）。SP-32（409）本走行・記録走行・確認走行ではコントローラを操作できない状態にする。SP-04（345）規定された操作以外の操作を受けずに自律走行できること。TM-07・09（547-549）手押し走行・マニュアル走行の定義。SR-05（579）停止線などでの自律停止と再開操作は自律走行のまま。
- 【事実】本走行で手押しが明示的に許される箇所は、朱色路側帯の手順（TK-41、81-86：自律停止→非常停止→台車で手押し→自律走行を再開）である。TK-70 にはこのような本走行の手順としての書き方がない。
- 【推測（根拠は強い）】TK-70 は実験走行日の「データ取得や単なる移動」の横断のための規定で、本走行で使えるものではない。本走行で手動・手押しで横断すれば、EV-19（意図的に触れた・操作を加えた）と SP-32 に当たり走行失敗になると読める。選択課題B を実施しないロボットは、TK-77 のとおり「オペレータ操作により走行開始」する、つまり規則の再開操作で自律走行のまま横断する。したがって TK-66 の「自律走行で横断するすべてのロボット」に入り、待機列に並ぶ義務がある。
  - ただし規則の本文は「TK-70 は本走行に適用しない」とは明記していない。人の確認が要る（§8 の Q4-1）。
- 【事実】確認走行区間の 2 ヶ所の横断歩道（TK-50 の 2、105-107）は「道路端から 1.5 m 以内で自律的に一時停止した後、オペレータ操作により走行を再開」。停止線・待機列の記載はない（信号の有無も本文にない）。ここは待機列の対象ではなく、道路端の停止だけと読める。
- 【事実】規則の本文に、追い越し（TK-69 の違反）そのものを失敗とする EV の項目はない（EV-14〜27）。失敗につながるのは、90 秒の停滞（EV-25）、ロボット同士の衝突による非常停止（EV-29、335：原則失敗）、車道への進入（EV-16）である。追い越しの扱いは委員の判断になると推測する（Q4-2）。
- 【事実】本走行は 2 台ずつ同時にスタート（TK-45、95）。DEC-329 の人の申告（model.yaml:61177）では 5〜10 分おきに出走し、追い越す・追い越される状況がある。列に出会う頻度の実績は記録にない。

## 4. 選択肢

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **案1（推奨）列の段階 `queue_follow` を DEC-343 に足す** | 停止線の手前の区間（「列の入口」の waypoint〜停止線）を、経路を固定した区間にする。経路は waypoint セットに人が描く直線（車道側に寄せる）。この区間では経路の引き直し・recovery（spin・backup）・滞留から抜ける段階（DEC-310）をしない。前方の箱（列の幅×奥行き、値は tbd）に障害があれば motion_hold で止まり、空いたら自動で進む。停止線に着いたら `rule_stop_hold`（DEC-343）へ。実現は、controller_server の FollowPath に固定の経路を渡す形を推奨（Nav2 の中で動き、速度の上限・平滑化の経路を通る） | 追い越しを構造で防ぐ（引き直しがない）。前進は自律（DEC-345 に合う）。EV-25 の 90 秒に、空いたら即進むことで対応 | 部品が増える（区間の属性・段階・前方の占有の判定）。列の入口より後ろまで列が延びていると、入口の前の普通の区間で回り込む |
| 案2 Nav2 のまま通路を狭める | 列の区間だけ keepout の通路（REV-137 の areas）を車体幅＋余裕にして回り込めなくし、BT の recovery を wait だけにする | 新しい制御はほぼ不要 | 前が塞がると goal の位置が占有され NavFn が失敗 → BT の recovery → goal の失敗 → goal_retry の繰り返しになり、動きが不確定。通路が広すぎれば追い越す、狭すぎれば推定のずれで通れない |
| 案3 取り入れない（DEC-343 のまま） | 列に出会わないことに賭ける | 作業なし | 列に出会うと、Nav2 は停止中のロボットを障害として回り込む（TK-69 違反、車道側の列を避けて歩行者側・車道側へ出る恐れ）か、goal（停止線）が先頭のロボットに占有されて計画に失敗し、recovery の backup で後ろのロボットに近づく。人はボタンで助けられない（DEC-345） |
| 案4 手動・手押しで横断（TK-70） | 本走行で横断だけ人が動かす | 列も停止位置も不要 | §3.1 の読みでは本走行では EV-19・SP-32 で走行失敗。**不採用を推奨**（読みの確認は Q4-1） |
| 案5 列の中を人のボタンで少しずつ進める | 止まるたびに人が再開 | 実装が小さい | DEC-345 の人の回答で失敗（再開ボタンは停止線の後・青信号の後だけ）。不採用 |
| 案6 KUAMS の lineup をそのまま移す | cmd_vel を直接出す | 実績のある形（推測） | gouda の指令の経路（速度の上限・平滑化・診断）を迂回する。2D の箱は低いロボットや横にずれたロボットを見落とす。不採用を推奨（考え方だけ案1に取り込む） |

推奨の理由：規則上、gouda（課題B を実施しても、しなくても）は待機列に並ぶ義務があると読め（TK-66・TK-77）、手動・手押しは本走行で失敗になると読める（EV-19・SP-32）。列の中の前進は人が助けられない（DEC-345）。Nav2 は既定で停止中のロボットを回り込むので、列の区間だけは経路を固定する必要がある。

## 5. 振る舞いの違いと、影響を受ける ID

- 案1：停止線の手前の区間で、前にロボット・人がいると、その後ろで止まり、空けば進む。経路は描いた直線から外れない（回避しない）。停止線と道路端の停止・再開は DEC-343 のまま。
- 列の区間では、滞留から抜ける段階（DEC-310・DEC-344）、goal_retry の経路の引き直し（DEC-307）、BT の recovery（PRM-18）を止める。DEC-344 (2)「stop の waypoint は飛ばさない」と同じ向き。
- 影響を受ける ID：DEC-343（段階の追加・区間の属性）、DEC-332、DEC-345、DEC-346（停止位置の実測に列の区間を足す）、DEC-310・DEC-344・DEC-307、DEC-305（自動の待機をしない方針の中の段階）、IFD-41（waypoint セット：区間の属性・列の経路）、IFD-40（motion_hold）、ND-03（mode_manager）、ND-10（Nav2）、PRM-11・18・69・72、TR-10、SR-37〜43、Q-B1・Q-B2・Q-G3・Q-G12、M-029（SRC-X01-0031）。
- waypoint のデータの形を変える（区間の属性 `queue`、または `kind` の値の追加と列の経路）。DEC-343 は「データの形は変えない」としていたので、これは承認事項。

## 6. ハザードと安全上の根拠（重大なものは警告の有無にかかわらず挙げる）

1. **追い越し・回り込み**（重大）：Nav2 の引き直しで列を回り込むと TK-69 違反。列は車道側に寄るので、回り込む側によっては車道への進入（EV-16 失敗）、歩行者の通路への進入（TK-39）。案1 は引き直しをしないことで防ぐが、列の入口より後ろでは防げない。
2. **前のロボットへの衝突**（重大）：EV-29 でロボット同士の衝突による非常停止は原則失敗。前方の判定の見落とし（低いロボット、黒く反射の弱い外装、LiDAR の近距離の死角、列が横にずれていて箱の外）で接近する。gouda は collision_monitor を動かしていない。
3. **後ろへの接触**：BT の backup（後退）が列の中で動くと後続に当たる。案1 では列の区間で recovery を止める。
4. **滞留から抜ける段階の誤作動**（重大）：costmap の消去（段1）で前のロボットを一時的に忘れて進む、inflation を小さくして（段2）すき間を抜ける。列の区間では止める必要がある。
5. **空いているのに進まない**：判定が人（随行員・委員・列の横に立つチームメンバー）を障害とみなし続けると、EV-25 の 90 秒で失敗の恐れ。逆に箱を狭くすると見落とし（2）。「前のスペースが空いた」の定義は規則にない（Q-B1）。
6. **停止線の帯の超過**（重大）：奥 0.5 m を越えると EV-22。列から停止線へ進む最後の動きで、goal の判定 0.25 m・推定のずれ・停止の遅れが重なる。道路端は越えると車道で、横断歩道の段差（DEC-349）もある。
7. **PC の出力の中立化は車体全体の停止の保証ではない**：motion_hold で中立にしても、ESP32 で優先される手動操作・ESP32 や駆動系の故障・慣性・斜面で動きうる。列の中の停止を「PC が中立を出した」ことで保証したことにしない。
8. **受信途絶の watchdog は誤指令を検出しない**：PC 指令の timeout 700 ms・ESP32 の watchdog 1 s（intent.md 103 行）は一定時間の未受信だけを検出する。前方の判定が誤って「空き」を出したときの前進は検出しない。
9. **推定のずれ**：交差点付近は人とロボットが多く、推定が乱れやすい（トピック1）。固定の経路は地図の上の線なので、推定がずれると実際の列からずれる。
10. **手動・手押しの横断**：本走行で行えば EV-19 で失敗と読める（Q4-1 が決まるまで運用に入れない）。

担当：人が実車を操作し、試験の条件と合否の基準を決める。AI は手順・解析スクリプト・設定への反映を担当する。値は証拠（rosbag・条件・日付・スクリプト）がそろうまで tbd。計算機は VM（DEC-333）。

## 9. 他のトピックとの依存

- トピック1（推定不能で止まらない）：列の区間で推定が乱れたときの扱い。固定の経路は推定に依存するので、`localization_wait` との優先の順（提案 §2）に `queue_follow` を入れる必要がある。
- トピック2（区間ごとの goal・失敗区間の再送）：DEC-343 の区切りと同じ仕組み。列の区間で「再送＝経路の引き直し」をしないことを決める必要がある。
- トピック3（skip 条件）：KUAMS の skip（waypoint の近くに点があれば次へ）を、列の区間・停止線の waypoint では使わない（DEC-344 (2) と同じ）。
- トピック5（速度・旋回の上限と collision_monitor）：collision_monitor の approach・stop の多角形を入れるなら、列の前方の判定に使える（前のロボットの後ろで止まる・空けば進む）。速度の上限は列の区間の速度と同じ実測で決める。
- トピック6（GLIM 軌跡から waypoint 候補）：停止線・道路端・列の経路（車道側に寄せる直線）の座標を地図に正しく置く道具。白線テープの位置を GLIM の地図に載せる手順が要る。

## 10. 実装するなら変える範囲の見積り（コードは書かない）

- `gouda_core/gouda_core/waypoints.py`：区間の属性（列）と列の経路の点列、検査（停止線の stop で終わること）。小。
- `autonomy_core.py`（ROS に依存しない判断）：区間の分け方、前方の占有の判定（箱・連続回数）、段階の遷移。単体試験つき。中。
- `autonomy_client.py`：列の区間で FollowPath（controller_server）に固定の経路を送る、または NavigateThroughPoses の区切り（DEC-343）と切り替える。中。
- `mode_manager_node.py`／`mode_core.py`：段階 `queue_follow` と motion_hold の出し入れ、列の区間で DEC-310 の段階を止める、ログと processing_state。中。
- `nav2_config.py`：FollowPath を使うなら変更は小。collision_monitor を入れるならトピック5 と合わせて中。

- `design/model.yaml`（revision 経由）：ST・TR・IFD・PRM の追加、M-029 の設計状態。試験：`gouda_core/test/stack.sh` のシミュレーションで箱を出し入れする試験。
