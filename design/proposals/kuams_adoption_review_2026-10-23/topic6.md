## 1. 問い

地図作成の走行の軌跡（変換後地図と一緒に保存される `trajectory_imu.txt`）から、waypoint の候補（位置・向き）を自動で作り、人が直してから保存する道具を、gouda の waypoint タブに足すべきか。

## 2. gouda の現状

【事実】waypoint タブ（`gouda_core/web/app.js:386-565`）
- 地図の上をクリックすると点が 1 つ追加される。値は常に `yaw: 0, kind: 'pass'`（`app.js:529`）。
- 新しい区間の速度上限には、一つ前の区間の値を写す。最初の区間は空（`app.js:530`）。
- 向き・kind を直す UI、途中の点の移動・削除、redo、距離の表示はない。「最後の点を削除」と「全消去」だけがある（`app.js:542-547`）。
- 地図作成の終わりの姿勢（DEC-289）は、黄の矢印で表示され、初期位置の候補にできる（`app.js:395-407`、`map_convert.py:351-375`）。
- 軌跡そのものは画面に描かれない。帯の地図（corridor_overlay.png）として間接的に見えるだけ。

【事実】データの形（`gouda_core/gouda_core/waypoints.py`）
- `Waypoint(x, y, yaw, kind)`。kind は `pass|stop`（`:39-44`）。
- 区間の速度上限は、全区間で正の数でなければならない。そうでないと保存は拒否される（`:61-62`）。つまり、空のままの区間がある候補は保存できない。
- 速度上限のほか、走行禁止・走行可の範囲も持つ（`:56`）。セットには、変換後地図の origin・版・内容ハッシュが付く（`:72-79`、RQ-I078）。
- 保存の流れ（`monitor_node.py:375-429`）：
  - 地図のハッシュを照合する。
  - 速度マスク（PRM-19・PRM-20 は未確定で、要求の中で値を渡す）と keepout マスクを作る。
  - waypoint が帯の外にあるか、禁止範囲の中にあるかを確かめる。どちらも警告だけで、保存はする（DEC-215）。

【事実】軌跡と地図の座標系
- 変換後の各版に、原図の `traj_imu.txt` の写しが `trajectory_imu.txt` として入る（`map_convert.py:36-37, 591-593`）。
  - 中身は GLIM の IMU の姿勢で、ループ閉じ込みの補正後のもの、map frame の TUM 形式（`:41`）。
- 走行に使う 2D 地図（map.yaml、案 C の帯）は、この軌跡を base_link に直した経路（`base_path`、`:343-348`）の両側 PRM-96 の範囲を空きにして作る（`:416-440`）。
  - PRM-96 = 1.0 m、承認済み（`model.yaml:46219` 以降）。
  - 3D 点群地図も同じ GLIM の map frame にある（`:25`）。
- **結論：その地図の軌跡は、その地図と同じ座標系にある。追加の位置合わせはいらない**（同じ変換で DEC-289 が既に使っている）。
  - 条件 1：同じ origin（原図）の変換後地図に限る。別の走行で作った地図は座標系が別なので使えない。
  - 条件 2：/config の写しがないと base_link に直せない。この場合 DEC-289 と同じく理由を出して作らない（`map_convert.py:371-372`）。
- 軌跡の点の間隔は普段は約 0.1 m だが、LiDAR が途切れた所では 2.7〜12.6 m 跳ぶ（`model.yaml` の PRM-97 の software_trial_basis）。PRM-97 = 5.1 m を超える跳びは帯をつながない。

【事実】走行の側（waypoint の密度と向きが効く所）
- 残りの waypoint を全部、NavigateThroughPoses の goal 1 つで送る（`autonomy_client.py:272-289`）。
- 上流の planner_server は、引き直しのたびに goal の全部の点について順に経路を引く（`design/research/upstream_jazzy/nav2_planner/src/planner_server.cpp:413-431`）。
  - 引き直しは PRM-103 = 1 Hz。
  - **点が多いほど、1 回の引き直しが重くなる。**
- RemovePassedGoals は先頭の点から、半径 PRM-11 = 0.7 m 以内の点を消す。最後の点は消さない（`remove_passed_goals_action.cpp:71-78`、`bt_params.yaml`）。
- goal の判定は xy 0.25 m・yaw 0.25 rad（上流の雛形 `nav2_params.yaml:92-96`）。
  - 【推測】このため、最後の waypoint（DEC-343 が承認されれば、区切りの終わりの `stop` の waypoint も）の yaw は実際の動きに効く。今の UI は yaw 0 で置くので、最後に +x の向きへ回る恐れがある。
- 関係する未決の項目

  - DEC-344：区間の属性に inflation を足す。`stop` は飛ばさない。
  - DEC-346：止まる位置の実測。
  - 提案 `proposals/state_transition_redesign_2026-10-23.md` §4・§5。
- intent.md:14 は「人間が waypoint と区間の速度上限を設定して保存ボタンを押す」とする。

## 3. KUAMS が実際にしていたこと

【事実：コードで確認】waypoint_editor の自動追加（`waypoint_editor_tool.cpp`、`waypoint_editor_panel.cpp`）
- 入力：自己位置の topic を購読する。既定は `amcl_pose`、型は PoseWithCovarianceStamped か PoseStamped（tool:50-52、panel:205-215）。
- 座標系：TF で `map` に変換する（tool:230-250）。
- 間隔：直前の waypoint からの**直線距離**が `auto_min_distance`（既定 1.0 m。パネルで 0.01〜1000 m）以上になったら 1 点足す（tool:204-213、panel:192-196）。
  - 曲がり具合のしきい値はない。止まっている間は点が増えない。
- 向き：その時点の自己位置の向きをそのまま使う（tool:217 `wp.pose = pose_map`）。進む方向（接線）ではない。
- 機能のコマンド（skip・wait など）は空のまま（tool:218）。後から手で書く。
- 編集：undo・redo は、変更ごとに waypoint の列全体の写しを積む方式（`waypoint_sequence.cpp:79-119`）。
  - 直前の区間の距離と総距離を表示する（tool:532-596）。
  - ドラッグでの移動・回転、右クリックでの削除・ID の変更・コマンドの編集、全消去ができる（README.ja.md）。
- 逆走・跳び・止まっている所・往復を見分ける処理はない。

【事実：時期】
- 自動追加・Clear のコミットは 2025-11-28。undo・redo・距離の表示は 2025-11-17。
- KUAMS が参加した日は、実験走行の 11/9 と 12/5・12/6、本走行は 12/7（`research_notes/tc2025_他チーム公開コード/kuams_文献調査.md:54-70`）。

【推測】
- 本走行の waypoint を自動追加で作ったかは、公開されていない。
- JRM 37(6) の「手で約 1.0 m 間隔」（同上:94）は大学構内の試験で、自動追加ができる前の話。
- 既定値 1.0 m は、この手作業の間隔に合わせたものと推測する。

前提の違い
- KUAMS は waypoint_navigator が NavigateToPose を 1 点ずつ送る（`waypoint_manager/waypoint_navigator/src/waypoint_navigator.cpp:32,118`）。密にしても planner の負荷は増えない。gouda は全点を NavigateThroughPoses で送るので、密度がそのまま負荷になる。
- KUAMS は自己位置（NDT）の topic から記録する。gouda の候補の元は地図作成そのものの軌跡なので、帯の地図（案 C）の中心線と一致する。
  - KUAMS の方式では、記録の走行の推定のずれがそのまま waypoint に入る。
- gouda には区間の速度上限と範囲（keepout）があり、kind は pass/stop だけ。KUAMS は点ごとのコマンド文字列で、速度上限は区間に持たない。

## 4. 選択肢

**案 A（推奨）：地図作成の軌跡から候補を作り、waypoint タブの編集欄に読み込む。保存は今のまま人が押す。**
- 手順
  1. 人が地図と版を選ぶ。
  2. 「軌跡から候補を作る」を押す。
  3. 軌跡を base_link に直す（`base_path` と同じ変換）。
  4. 下の規則で間引く。
  5. 候補を `wpState.points` に入れ、速度上限は全区間を空にする。
  6. 人が見て直す。
  7. 保存（今の検査・警告がそのまま働く）。
- 間引き：**弧長（たどった距離）の順に**間引く。場所による重複除去は使わない。往復の行きと帰りを一つにまとめてしまうため。
  - 1 点残すのは、前の点からの弧長が Δd_max 以上になったとき、または向きの変化が θ_max 以上で、かつ弧長が Δd_min 以上になったとき。
  - 必ず残す点：始点、終点、跳びの前後、逆走が始まる所と終わる所。
  - Δd_max・θ_max・Δd_min は道具の入力値で、既定値を持たない。人が入れ、manifest の generator に記録する。地図タブと同じく「数値はコードに置かない」。
  - KUAMS の 1.0 m は参考として画面に示すだけにする。
- 向き（yaw）：間引いた後の折れ線の接線（次の点への向き。最後の点は前の点からの向き）。
  - 軌跡の車体の向きは確認だけに使う。接線と 90 度以上違う所は「後退していた」として警告する（allow_reversing false）。
- 走行の経路でない部分：自動では消さない。印を付けて人に選ばせる。
  - 印を付けるもの
    - 跳び（PRM-97 を超える／超えない跳びを分けて示す）
    - 止まっていた所（時刻と位置から求めた速さが小さい所）
    - 逆走
    - 同じ場所を別の向きで再び通った所（往復・ループ）
  - 人がすること：始めと終わりの番号を選ぶ（スタートまで運んだ所、地図作成の終わりの所を切る）、範囲を消す、点を動かす。
  - 折り返し地点（TK-18）の U ターンは本物の経路なので、自動で消してはいけない。
- kind：すべて `pass` で作る。停止線・道路端（TK-12、TK-19、crosswalk_2026 の停止線 1・2、道路端 1・2）は自動で見つけない。
  - 人が、公開されたコース図と現地の白線をもとに、候補の点を選んで `stop` にする。
  - 補助として、保存の前に stop の数を表示する。
- 速度上限：空のまま。既存の validate が、空の区間がある候補の保存を拒否する（意図どおり）。
  - 何百もの区間に値を入れやすくするため、「区間 i〜j に人が入れた値を入れる」操作を足す。既定値は持たない。
  - DEC-344 の inflation も、足される場合は同じく空のまま。
- 編集機能の追加（候補が数百点になるので必要）
  - 途中の点の削除・移動
  - kind の切り替え
  - 向きの矢印の表示
  - 区間の距離・総距離
  - redo
  - 範囲の削除
- 理由
  - 帯の地図（案 C）の空きは、地図作成の軌跡の周り 1.0 m だけ。手でクリックすると中心から外れやすい（DEC-215 の警告の元）。軌跡の上の点は、作りからして帯の中心にある。
  - 座標系の位置合わせがいらない。
  - 追加の走行もいらない。地図作成の走行がそのままコースに沿っていれば、手間が一番少ない。

**案 B：地図ができた後に「経路を教える走行」を手動で行い、自己位置推定の姿勢から記録する（KUAMS に近い）。**
- 長所
  - 地図作成用の走り方（遠回り、ループ閉じ込みのための往復、ゆっくり蛇行）と関係なく、本番で通らせたい横の位置・順番で走れる。
  - 停止線で人が「ここが stop」と押せば、実際の位置で stop の印を付けられる。
- 短所
  - gouda の自己位置推定（ND-07・ND-08）は自律走行の開始（TR-05）で起動する。手動モードでは動かない。
  - 手動のまま推定を動かすには、モードとノードの起動の変更が要る（RQ-I065 の 4 モード、intent.md の「競合する推定器を同時に有効化しない」）。承認が要る。
  - 推定のずれや推定不能が記録に入る。帯（地図作成の軌跡）から外れた点は DEC-215 の警告になる。
  - 走行が 1 回増える。
- 変形 B'：教える走行を rosbag に記録する。VM で、その地図に対して推定を再生し（`gouda_core/test/stack.sh`）、出てきた姿勢の列を案 A と同じ道具に通す。
  - 車体のモードは変えない。ただし、再生の環境づくりと時間がかかる。

**案 C：stop の印だけ、地図作成の走行中に記録する（案 A に足す）。**
- 地図作成モードの monitor に「ここに停止線」ボタンを置き、押した時刻を記録する。変換の後、その時刻の軌跡の姿勢を stop の候補にする。
- 軌跡はループ閉じ込みの補正後のものなので、時刻で引いても同じ座標系にある。
- 地図作成のモードに UI の操作を足すので、承認が要る。

**案 D：取り入れない。今のまま手でクリックする。**
- 点の数が少なければ、planner の負荷は小さい。
- ただし、yaw 0 の問題（§2）と、帯から外れやすい問題は残る。

## 5. 振る舞いの違いと、影響を受ける ID

- 道具そのもの：走行時の振る舞いは変えない。保存の形（`waypoints.py`）・内容ハッシュ・検査も変えない。
  - 変わるのは人の作業の手順（intent.md:14 の「人間が設定する」が、「候補を見て直す」になる）。
- 保存されたセットを通じて変わるもの
  - waypoint の数と間隔、yaw（接線の向き）。
  - このため、Nav2 の NavigateThroughPoses の点の数、経路の形、最後の点・stop の点での回転が変わる。
- 影響を受ける ID：IFD-30（waypoint セット）、IFD-41（速度マスク：区間の数が増えると、帯の重なりの警告も増える）、IFD-13・ND-10（点の数と planner の負荷）、PRM-11、PRM-103、PRM-19・PRM-20、PRM-96・PRM-97、DEC-215、DEC-289、DEC-343、DEC-344、DEC-346、RQ-I078、RQ-I011、ND-03（区切り）。
- 案 B は、ND-07・ND-08 の起動の条件と、TR-03・TR-05 に影響する。案 C は MODE-MAP の UI と IFD-35（原図と一緒に残す記録）に影響する。

## 6. ハザードと安全上の根拠（警告の有無にかかわらず挙げる）

- H1 走行の経路でない部分（遠回り、スタートまでの移動、往復、撮り直し）が候補に残り、そのまま保存される。
  - 結果：コースを外れる。車道への進入（TK-14）。確認走行区間でのコーンへの接触。
  - 対策：自動では消さない。印を付ける。保存の前に、人が全体を目で見て確かめる。対策は「人が見る」ことだけで、道具は正しさを保証しない。
- H2 跳び（LiDAR の途切れ）の前後を直線でつなぐと、実際には通っていない所を通る。
  - 2.7〜5.1 m の跳びは、帯の地図でもつながれているので気づきにくい。
  - 対策：補間しない。跳びを示し、人に選ばせる。
- H3 kind: stop を付け忘れる、またはずれた所に付ける。
  - 結果：停止線で止まれず、走行失敗（TK-22、TK-23、EV-22）。DEC-344 で stop を飛ばさないことにしても、付け忘れは防げない。
  - 対策：自動で見つけたことにしない。stop の数と位置を、人がコース図と照らし合わせる。止まる位置の精度は DEC-346 で実測する。
- H4 速度上限を道具が埋める、または一括の入力で慣例値が広がる（1.5 の違反になりうる）。
  - 対策：空のままにする。保存の拒否は既存の validate が行う。一括の入力にも既定値を置かない。
  - 停止の前の早めの減速（TK-25）の区間の値は、トピック 5 と DEC-346 で決める。
- H5 点が多すぎると、引き直しが重くなる（`planner_server.cpp:413-431` で全点について順に経路を引く）。
  - 結果：経路が古いまま走る、または planner が失敗して goal_retry や滞留になる（3 分の滞留は失敗、intent.md:1）。
  - 【推測】数百〜2000 点程度で問題になる可能性がある。実測が要る（§7 M1）。トピック 2 の区切りで上限を設ける案と組みになる。
- H6 yaw の誤り：後退していた所の向きや yaw 0 を使うと、最後の点・stop の点で車体がその場で回る（yaw 0.25 rad の判定）。
  - 結果：停止線の帯の中で向きを変え、奥 0.5 m を越える恐れ（【推測】）。
- H7 地図の取り違え：別の origin の軌跡を使う。
  - 対策：選んだ変換後地図の版の `trajectory_imu.txt` だけを使い、内容ハッシュをセットに記録する（既存の RQ-I078）。
- H8 地図作成のときの横の位置が、本番に向かない。
  - 例：縁石・車道の側に寄っていた。そのときにはなかった駐輪車や工事があった。
  - 帯の中心だからといって安全とは限らない。人が点を動かして直す。
- 根拠の前提：この道具は「人が見て直す」ことを前提とする。道具の検査（警告 0 件）は、経路が正しいことの証明ではない。
  - 停止の保証については、PC 出力の中立化も、受信途絶の watchdog も、この道具とは関係しない。誤った waypoint（誤指令の一種）は watchdog では検出できない（1.5）。

## 7. 実測が要る値と、計測の手順の案

- M1 点の数と planner の負荷（AI が VM で行う。人の許可の後）
  - 手順：本物の変換後地図で、NavigateThroughPoses に N = 50・200・500・1000・2000 点を与える（軌跡から間引いて作る）。planner_server の 1 回の計算時間と、引き直しの間隔に収まるか（PRM-103 = 1 s）を記録する。
  - 合否の基準の案：p99 の計算時間が引き直しの周期より十分短いこと。余裕の割合は人が決める（tbd）。
  - 決まるもの：Δd_max の下限、または区切りあたりの点の数の上限（トピック 2）。
- M2 間隔と追従のずれ（実車または VM の再生）
  - 手順：同じ区間を Δd の 2〜3 通りで走り、経路（plan）と軌跡の横のずれ、曲がり角での内側への切り込み、帯の外に出た時間を比べる。
  - 合否：帯（PRM-96）の中に収まること。値は tbd。
- M3 stop の位置の精度：DEC-346 の計測に、候補から作った stop を含める。
  - 停止線の手前 1 m〜奥 0.5 m（TK-23）に、車体の一部が入っているか。車体の前の端は footprint で base_link の前 0.55 m（PRM-69）。
- M4 軌跡と推定の一致（座標系の確認）
  - 地図作成の rosbag を VM で再生し、同じ地図で ND-07 の推定を出す。軌跡の上の点との距離（p50・p95）を測る。
  - 作りからして座標系は同じはずなので、これは確認の計測。差が大きければ、推定の側の問題として別の記録にする。

## 8. 分類と、決まらない場合に止まる作業

- **案 A の道具：承認（推奨）。**
  - 1.2 の自律判断の条件（外から見た振る舞いを変えない・後から戻せる・承認済みの契約の範囲内）には近い。道具の出力は、人が見て保存するまで走行に使われない。
  - それでも承認に回す理由
    1. intent.md:14 の作業の手順（運用）が変わる。
    2. 生成したセットは走行の入力（指令に関わるデータ）になる。
    3. 1.2 の「分類に迷うものは承認」。
  - あわせて、DEC-106 により、コードを変える前に人の「はい」が要る。
- 承認に含める小項目
  - (a) 向きを接線で付ける。手でクリックしたときも同じにするか（今の yaw 0 は最後の点で振る舞いに効く。外から見た振る舞いが変わる）。
  - (b) 速度上限を空のまま読み込み、一括の入力を足す。
  - (c) 編集機能の追加（削除・移動・kind・redo・距離）。
- 案 B・案 C：承認（モード・ノードの起動、または地図作成の UI を変える）。
- 実測：M1〜M4（間隔・点の数の上限・stop の位置）。判断台帳に実測の項目として登録する案。
- 自律判断でよいもの：道具の純粋な関数（間引き・跳び・逆走の判定）とその単体試験を、提案のディレクトリで下書きすること（1.7 の基盤。ただし DEC-106 の下では、実装の前に人に聞く）。
- 決まらない場合に止まる作業
  - 案 A が決まらない：自動の候補づくり。今の手作業での waypoint 作成は止まらない。
  - (a) が決まらない：最後の点・stop の点の向きの扱い。DEC-343 の実装の確認にも関わる。
  - M1 が決まらない：間隔の既定の目安と、トピック 2 の区切りの点の数の上限。

## 9. 他のトピックとの依存

- トピック 2（区間ごとに送る・再送）：密な waypoint を、NavigateThroughPoses 1 つに全部入れないための前提。区切りの単位（stop ごと、DEC-343）と点の数の上限（M1）を一緒に決める。
- トピック 3（skip の条件）：飛ばす単位は waypoint 1 点。間隔が狭いほど、1 回の skip は短い距離になる。stop を飛ばさない条件（DEC-344 (2)）は、候補で付けた kind に依存する。
- トピック 4（待機列か手動横断か）：停止線 1・2 と道路端 1・2（往路・復路）のどれを stop にするか。stop の候補の付け方（人が付ける／案 C）が関わる。
- トピック 5（速度・旋回の上限）：区間の速度上限は、この道具では空のまま。値はトピック 5 と人が決める。停止の前の減速区間（TK-25）も同じ。
- トピック 1（推定不能で止まらない）：【推測】地図作成の軌跡の上は、地図の点が一番よく取れている所なので、NDT にとって条件がよい。間接的に助けになる。
