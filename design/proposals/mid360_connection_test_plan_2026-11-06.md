# MID-360 の接続試験と動作確認の計画（提案、2026-11-06、第204便）

状態：**提案**。試験の条件と合否基準は人が決める（CLAUDE.md 1.12）。下の基準はすべて案で、未承認。
結果は台帳 `design/research/vehicle_pc/2026-11-06_mid360_connection/ledger.yaml` に書く。
公式資料はリポジトリの外の `TsukubaChallenge/Sensors/MID-360/official/`（著作物なので公開リポジトリに入れない。一覧は同じ場所の `INDEX.md`）。

関連：#72（統合の計画、段階 1 ドライバ・段階 6 実車）、#31（ステー・放熱）、#74（見える範囲）、#77（アーキテクチャ案）、`MID-360_stay/README.md`。

## 1. 目的

1. MID-360 が電源・Ethernet でつながり、点群と IMU のデータが出ることを確かめる
2. ROS 2 Jazzy で PointCloud2 が出て、周期・点数・frame_id・時刻が分かる
3. XT-32 と同時につないでも、XT-32 の点群が乱れない
4. 抜き差し・再起動のあとに戻ることを確かめる（sensor supervisor の設計の材料）
5. 発熱を測る（#31 のアルミ板の要否の判断の材料）
6. 取り付けの後：写り込み・地面の見え始め・傾きを測る（TF の値の材料。#72 段階 3）

やらないこと：Gouda の起動・停止、車体が動きうる指令、製品のコード・設定（setup.sh、drivers.repos、/config）の変更。これらは人の指示と承認（DEC-106）の後。

P0〜P3 はリポジトリにも車載 PC の設定にも手を入れずにできる。P4 以降はドライバの導入が要る（Q4）。

### 試験の PC（DEC-431：「dellのx86機でテストを行います」）

試験は x86 の車載 PC（Dell G15、Ubuntu 24.04）で行う。AI が読むだけで確かめた状態（2026-11-06）：

- 有線の口は内蔵の 1 つだけ。USB-LAN はつながっていない
- その口に、LiDAR 用の固定アドレスの接続の設定が 2 つある（どちらも自動接続あり、MID-360 の工場出荷時と同じサブネット、PC 側のアドレスは別々）。どちらが有効になるかで、ドライバの config の `host_net_info` に書くべき値が変わる
- CPU は AVX2 あり（Livox Viewer 2 の条件を満たす）
- Livox Viewer 2 がホームにすでに置かれている（2026-11-06 21 時台。アドレスのない口、例えば tailscale0 で落ちる問題を避ける LD_PRELOAD の仕組みつき。誰が置いたかは記録にない）
- Livox-SDK2 は /usr/local に入っていない。AI の ssh の利用者はパスワードなしの sudo を持たない
- 確かめた時点で Gouda は動いていなかった

これにより：
- P2〜P4：XT-32 の LAN ケーブルを抜き、MID-360 を内蔵の口に直結する。どちらの接続の設定を使うかは人が決めて有効にする（ネットワークの設定の変更なので AI はしない）
- P3：Viewer 2 は画面が要るので、人が Dell の前で `~/LivoxViewer2/run.sh` から起動する
- P5：口が 1 つなので、PoE なしのスイッチで XT-32 と MID-360 をまとめる（DEC-432：「Non-PoE switch」）。同じ口・同じサブネットなら経路の取り合いは起きない（2 つの口に同じサブネットを置く問題は、この PC では起きない）。3 つのアドレス（PC・XT-32・MID-360）が重ならないことを P2 で確かめる
- ~/gouda_ws と Gouda の起動・停止には触れない。Gouda が動いていたら、`/mode/state` を確かめて人に聞く

## 3. 手順と合否基準（案）

各項目の ID は台帳と同じ。基準の数値は仕様の値（4 章）から作った案で、許容の幅は人が決める。

### P0 受け入れ・目視
- T00-1 外観：窓の傷・汚れ、コネクタのピンの曲がり、ケーブルの付属品を写真で記録
- T00-2 シリアル番号の記録（台帳には書かない。ローカルのメモのみ。工場出荷時のアドレスがシリアル番号から決まるため）
- T00-3 ケーブルのピン配置を、マニュアルの図と現物で突き合わせる（電源の極性。テスターで導通）
- 基準：傷・曲がりがない、ピン配置がマニュアルと一致

### P1 電源
- 安定化電源で、電流の制限をかけて給電する（電圧と制限値は Q3）。制限が起動時の 18 W（12 V で 1.5 A。計算）より低いと起動しない可能性がある（推測）
- T01-1 起動時の最大電流と、10 分後の電流を記録（電源の表示。可能なら記録計）
- T01-2 電源投入から、点群が出始めるまでの時間（P3 か P4 で計る）
- 基準（案）：起動時・定常の電力が仕様（4 章）以内。電源の保護が働かない

### P2 リンク・アドレス
- Dell の内蔵の有線の口に直結する（XT-32 のケーブルは抜く）。PC 側は固定のアドレス（MID-360 と同じサブネット。既存の接続の設定のどちらかを人が有効にする。2 章）
- **注意**：XT-32 と MID-360 の工場出荷時は同じサブネット（`docs/gui_native_rviz.md` 45 行は VM の USB-LAN の例）。2 つの口に同じサブネットを置くと受信が不安定になりうるので、2 つ目の口を足す場合（Q2 の代替）は MID-360 を別のサブネットに移す
- T02-1 リンクの速度と全二重（`ethtool <if>`）
- T02-2 MID-360 のアドレスの確認（Livox Viewer 2 の一覧、または `tcpdump -i <if> -n udp` で送り元を見る）
- T02-3 `ping -c 600 -i 0.2`（2 分）で欠けと往復の時間
- 基準（案）：リンクの速度が仕様どおり、ping の欠け 0

### P3 Livox Viewer 2
- 試験用 PC（Windows か Ubuntu）に人が入れる。車載 PC には入れない（setup.sh の外の導入になるため）
- T03-1 点群が表示される。部屋の壁・床・天井が見え、視野の上下の端（-7°・52°）が分かる
- T03-2 IMU の値が出る（静止で重力の向き）
- T03-3 ファームウェアの版の記録。更新は人の判断（戻せないことがある）
- T03-4 アドレスの変更：DEC-432（同じサブネットのまま）により、PC・XT-32 とアドレスが重なる場合だけ行う。変更前後の値はローカルのメモに書く
- 基準：点群と IMU が出る

### P4 ROS 2 ドライバ
- ドライバ（DEC-442、方針。「一旦推奨案で行こう」）：公式の livox_ros_driver2 を commit で固定、Livox-SDK2 は Ubuntu 24.04 のビルドの修正の後の master の commit で固定。setup.sh と drivers.repos に足す（#72 段階 1。変更そのものは別に利用者の yes が要る、DEC-106）。build.sh は作業場所の build・install を消すので、~/gouda_ws とは別の作業場所でビルドする。2 番手は TU Darmstadt の fork（jazzy）
- 時刻（DEC-442）：まず同期なし。XT-32（PRM-55=1、DEC-083）と同じく PC の受信の時刻に乗る。足りなければ PTP（PC を親、Dell の口はハードウェアの時刻の記録に非対応なのでソフトウェアの方式）に進む
- 起動は `ros2 launch livox_ros_driver2 <launch>` のみ。Gouda は起動しない
- T04-1 topic の一覧・型・frame_id（`ros2 topic list -t`、`ros2 topic echo --once` の header）
- T04-2 周期（`ros2 topic hz` を 60 s）。点群と IMU
- T04-3 1 枚の点数・field（x,y,z,intensity,tag,line,timestamp など）（`ros2 topic echo --once --field fields` と点数）
- T04-4 帯域（`ros2 topic bw`）、ドライバの CPU（`top -p` を 60 s）
- T04-5 時刻：header.stamp と受信の時刻の差（解析スクリプト、未作成）。同期なしの時刻の扱いを資料と突き合わせる
- T04-6 rosbag を 60 s 記録（点群・IMU）。生のログはリポジトリに入れない（1.10）
- 基準（案）：周期が設定どおり（10 Hz の場合 ±5%）、点数が仕様の点/秒÷周期の ±10%、IMU が仕様の周期、時刻の差が一定（ずれが増えない）

### P5 XT-32 と同時に
- PoE なしのスイッチ（DEC-432）で XT-32 と MID-360 を Dell の口にまとめ、同時に動かす。スイッチに PoE がないことを型番か表示で確かめてからつなぐ。車体で行う場合、車体は止めたまま、Gouda は起動しない。動いていたら `/mode/state` を確かめて人に聞く
- T05-1 XT-32 の点群の周期・点数が、MID-360 なしの時と同じ
- T05-2 MID-360 の周期・点数が P4 と同じ
- T05-3 2 つの点群を rviz2 で重ね、同じ壁がおおよそ重なる（TF は仮の値）
- T05-4 時刻の差（DEC-442）：同じ壁を両方で見た rosbag から、XT-32 と MID-360 の header.stamp の差の平均と揺れ、受信の遅れを出す（解析スクリプト、未作成）。足りなければ PTP に進む（足りるかの基準は人が決める）
- 基準（案）：どちらの周期・点数も P4・単独時から ±5% 以内。T05-4 は記録のみ

### P6 抜き差し・再起動
- T06-1 Ethernet を抜いて 10 s 後に戻す：点群が戻るか、戻るまでの時間、ドライバのログ
- T06-2 電源を切って 10 s 後に入れる：同上
- T06-3 ドライバを止めて起動し直す：同上
- T06-4 ドライバを MID-360 なしで起動したときの振る舞い（エラーで終わるか、待つか）
- 基準：判定しない（記録のみ）。sensor supervisor（ND-18）の設計の材料にする

### P7 長時間・発熱
- 机の上で 60 分動かす。取り付けの条件（ステーだけ、アルミ板あり）は Q6
- T07-1 底面・上面の温度を 10 分ごと（非接触の温度計か熱電対）、周囲の温度
- T07-2 60 分のあいだの周期・点数の変化、ドライバのログの警告
- 基準（案）：底面の温度は記録のみ（判断は人。#31）。周期・点数が P4 から ±5% 以内

### P8 取り付けの後（ステーの取り付けの後）
- 車体は止めたまま、平らな所。Gouda は起動しない
- T08-1 車体の写り込み：足跡の外に出る点の位置（切り取りの箱の値の材料）
- T08-2 地面が見え始める距離（#74 の計算と比べる）
- T08-3 傾き：地面の当てはめと内蔵 IMU の重力から roll・pitch（#72 の方法 1・2）。0.5° 以内で一致するか
- T08-4 ステーの寸法と CAD の差
- 基準（案）：T08-3 は 2 つの方法の差 0.5° 以内。他は記録のみ

これらから、試験で特に見ること：

- **P0**：型式ラベルが Mid-360（S・L ではない）か。分岐ケーブルの電源の色
- **P2**：PoE のハブ・スイッチを使わない。車載 PC の XT-32 の口と同じサブネット（2 章）
- **P3**：Livox Viewer 2 は AVX2 の CPU が要る。Windows はファイアウォールで見つからないことがある（UM p18・p20）
- **P4**：xfer_format を 0 にしないと PointCloud2 が出ない（launch の既定は 1）。同期なしの header.stamp は PC の受信の時刻なので、ROS の時刻とは合うが、受信までの遅れと揺れが入る（T04-5 で測る）。config の JSON を変えたら build.sh をやり直す（install 先にコピーされるため。RD #116）。build.sh はワークスペースの build・install を消すので、専用のワークスペースにする
- **P4・P8**：JSON の `extrinsic_parameter` は 0 のままにする。傾きを JSON と TF の両方に入れると二重に回る（#77 の「TF の発行元を 1 つにする」と同じ）。前に誰かが本体に値を書いていないかも確かめる（本体に残るかは未確認）
- **P5・P8**：XT-32 の光と MID-360 の窓が真正面に向き合わない配置か（取り付けの前に人が確認）
- **P7**：底面 75 °C を上限の目安として記録
- Q4 の材料：公式 1.2.6 の build.sh 方式のほかに、colcon でビルドできる Jazzy 対応の fork（TU Darmstadt、atinfinity、CTU-MRS など）がある。比較は台帳の references.C と「forks」。どれを使っても版（commit）を固定する（1.11）
