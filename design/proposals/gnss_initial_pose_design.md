## 1. 流れ

```
地図作成（TR-03〜04）                         自律走行の準備（体験 9）                    開始（TR-05）
GNSS（位置・品質・向き）を記録 ──┐          GNSS の今の位置・向き                      初期姿勢 → ND-07
GLIM の補正後の軌跡（dump） ─────┴→ 対応の計算 → GNSS→地図の変換 ─→ 地図の座標の姿勢を表示 ─→ 人が確認・直す ─→（A3: Monte Carlo の探索で照合）
```

## 2. 地図作成のときの GNSS の記録（DEC-126。2026-10-18 許可・実装）

- mode_manager が地図作成の開始（TR-03）から終了（TR-04）まで、IFD-47〜49 を地図作成の作業フォルダに JSON Lines で書く（時刻、緯度・経度・高さ、PVT の mode、衛星数、水平精度、向きとその mode）。rosbag とは別に、原図と一緒に残すため。
- 地図作成の終了で原図（IFD-29）の横に `gnss.jsonl` として登録する。実装では GLIM の dump の内容ハッシュには含めず（その意味を変えないため）、`source_manifest.json` の `gnss` に SHA-256 と topic ごとの行数を書いた。記録するのは IFD-47〜49 と方位の共分散（AttCovEuler、IFD-50。§9 の品質判定に要る）。メッセージは全項目をそのまま辞書にして書く（受信機の時刻 block_header を含む）。
- GNSS がない・未受信でも地図作成は止めない（記録が空なら対応は作らない）。

## 3. GNSS と地図の座標の対応（承認事項 DEC-127。値は実測・承認）

- 地図の変換（ND-05）で計算し、変換後地図の manifest に `gnss_alignment` を書く。
- 手順:
  1. GNSS の記録のうち RTK fix（PVT の mode が RTK fix）の点だけを使う。
  2. 緯度・経度を、最初の点を原点にした局所の平面（ENU）に変える（ROS の geographiclib か pyproj。依存の追加は実装の時に確認）。
  3. 各 GNSS の点の時刻で、GLIM の補正後の軌跡から主アンテナの位置を求める（LiDAR の姿勢 × 静的 TF の lidar→gnss_link。時刻は補間）。
  4. 二つの点の列の 2D の重ね合わせ（回転と平行移動、縮尺なし。最小二乗、Kabsch）で、ENU → 地図 の変換を求める。高さは使わない。
  5. 残差（RMS と最大）、使った点の数、走行の範囲を記録する。
- 使ってよいかの判定（値は未確定。tbd、決定先 DEC-127）: 残差の RMS の上限、点の数の下限、範囲の広さの下限。判定を満たさないときは対応を「使わない」と記録し、開始の準備は人の指定だけになる。
- 地図の座標は GLIM の座標で、北の向きとは関係がない。対応の回転がその差を表す。

## 4. 開始の準備での表示と確認（承認事項 DEC-128）

- monitor の「自律走行の準備」の欄で、選んだ waypoint セットの地図に `gnss_alignment` があるとき:
  - GNSS の今の位置（主アンテナ）と向き（デュアルアンテナの heading）を、地図の座標の base_link の姿勢に変えて、地図に重ねて表示する（矢印。品質: RTK fix／float／単独、向きの mode、記録の新しさ）。
  - 初期位置の欄に GNSS の値を入れる（人は直せる）。「GNSS の値を使う」ボタンで入れ直す。
- 人の確認: 人が地図の上の位置と向きを見て正しいと判断したら「自律走行」を押す（押すことが確認。追加の承認の操作は加えない: RQ-I011・DR-09）。
- GNSS の値を使えないとき（fix でない、向きがない、対応がない）: 欄に理由を表示し、値は入れない。人の指定（今の入力）は常にできる（体験 9「人が初期位置や向きを設定することも可能」）。
- ND-07 の側（A3 の場合）: 渡された初期姿勢を中心に Monte Carlo の探索（ndt_align_srv）で照合し、収束の結果（score）を monitor に重ねて表示する（「位置の収束を人間が確認する」）。照合の結果の表示は ND-07 の実装（DEC-115 の後）。

## 11. ソフトウェアでの較正（第3版。DEC-132 の再検討）

人の指示（DEC-132、原文）: 「次の調査結果が出ていることから、再検討してソフトウェア較正の可能性を探れ」（調査結果の写し `design/research/gnss_calibration_research_2026-10-18.md`）。

### 11.1 結論（AI の推奨）

- **ソフトウェアで較正できる見込み**。T1（map→ENU）と T2（取付の方位）を分けずに、レバーアーム（主アンテナの水平位置）と時刻遅延も含めて、**一回のバッチの最小二乗で同時に推定する**（調査結果の定式化どおり）。人の手での校正は要らない。
- **基準の姿勢は、地図作成の走行の GLIM の補正後の軌跡**（traj_lidar.txt と静的 TF の base_link→LiDAR）を使う。調査結果は NDT の姿勢を使うが、Gouda では ND-07 がまだないこと、地図そのものが GLIM の軌跡の座標で作られていることから、地図作成のときの記録（DEC-126 で実装済み）だけで較正できる。NDT での再推定は ND-07 の後に検証として行う。
- 推定されるのは「その地図の base_link」から見たアンテナの位置と方位で、/config の LiDAR の取付の誤差も吸収される（調査結果の注意と同じ）。したがって**結果は地図の版と一緒に保存する**（変換後地図の manifest）。

### 11.2 合成のデータでの試算（FILE-GNSS-CALIB-FEASIBILITY。実データではない）

| 走行 | レバーアーム x・y | 取付 Yaw | 時刻遅延 | ant_z |
|---|---|---|---|---|
| S1 一方向の直線だけ | 決まらない（事前の値のまま） | 0.002 度の誤差 | **0.135 s の誤差なのに標準偏差は 0.0001 s** | 決まらない |
| S2 通常のコース（前進、緩い曲がり） | 誤差 5 mm・0 mm | 0.023 度 | 0.005 s | 決まらない |
| S3 較正の走行（8 の字、その場旋回、前進と後退、速度の変化、複数の向きで静止） | 誤差 1.4 mm・1.2 mm | 0.016 度 | 0.005 s | 決まらない |
| S3 で方位の定義を取り違えた（NED を ENU として使った） | — | 方位の残差 78.5 度（正しい定義では 0.34 度） | — | — |

分かったこと:
1. 較正の走行をすれば、調査結果の目安（レバーアーム 1 cm、取付 Yaw 0.1 度）より良く決まる（合成のデータなので楽観的。GLIM の軌跡の誤差は実際には時間的に相関する）。
2. ant_z は平地では決まらない（調査結果どおり。事前の値のまま残り、T1 の z に吸収される）。
3. **事後と事前の標準偏差の比較だけでは、可観測性を見誤ることがある**（S1 の遅延）。走行の内容（向きの変化の範囲、後退の有無、旋回の両方向）を数えて判定に加える。
4. 遅延は旋回で大きな方位の差になるため、**遅延の初期値を先に 1 次元の探索で決めないと誤った解に留まる**（試算の 1 回目で起きた）。
5. 方位の定義（§10 の未確定の点）の取り違えは、方位の残差ではっきり分かる（較正が定義の確認を兼ねる）。

### 11.3 設計の案

- 入力: 地図作成の走行の gnss.jsonl（DEC-126）と GLIM の dump（traj_lidar.txt）と、その時の /config（静的 TF）。RTK fix・方位の fix の点だけ、一定の間隔で間引く（値は tbd）。
- 推定: θ, t（map→ENU）、ant_x・ant_y、取付 Yaw、遅延。ant_z は /config の値に固定（推定しない）。事前の値は /config の取付位置（人の値。RQ-I081）と 0（取付 Yaw・遅延）。事前の標準偏差は tbd。
- 判定: 残差の RMS、事後の標準偏差、**走行の内容の数え上げ**（向きの変化の範囲、後退の距離、両方向の旋回）。値はすべて tbd（次の実機試験のデータで提案する）。判定を満たさない値は使わない（その地図は人の指定の初期位置だけ）。
- 出力: 変換後地図の manifest に `gnss_calibration`（各値、標準偏差、使った点の数、判定）。enu→map の static TF（DEC-131）はここから出す。
- 実行の場所: 地図の変換（ND-05、map_creator）の一部として、または地図タブからの再計算（変換の設定と同じ扱い）。
- 検証: 別の走行（次の実機試験の 2 回目、DEC-114）で残差を確かめる（調査結果の「別の日のデータ」）。
- 走行の仕方: 地図作成の走行の最初か最後に、上空の開けた所で較正の動き（8 の字、その場旋回の両方向、前進と後退、複数の向きで静止）を入れる。これは実機試験の手順で、人の判断（承認事項）。
- 基線長: 受信機が求める値（basevector の topic、既定で無効）を使うには、ドライバの設定を変える必要がある（承認事項。今回は入れない）。
