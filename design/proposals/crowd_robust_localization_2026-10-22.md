## 1. 今の構成（事実）と、言葉の整理

自律走行中は「SLAM（地図を作りながら走る）」ではなく、**事前地図の上での自己位置推定**になっている。LiDAR に頼る部分は二つある。

| 部分 | 中身 | LiDAR への依存 |
|---|---|---|
| odom→base_link（ND-08） | GLIM を odometry だけで動かす（LiDAR と IMU の密結合） | 点群の連続の照合。IMU だけでは数秒しか持たない |
| map→odom（ND-07、案 A3） | 前処理 gouda_a3_points（近く・遠くの箱の切り取りと voxel、PRM-79〜81・102）→ Autoware の NDT（事前の 3D 点群地図）→ Autoware の EKF | 走行中の点群と事前地図の照合 |
| GNSS（ND-19） | mosaic-go G5 P6、デュアルアンテナ、ネットワーク RTK（Point One） | なし。ただし**今は初期位置にだけ使う設計**（DEC-124）。走行中の融合（DEC-130 の仕様 T5）は対象外、発散の監視（T4、DEC-134）は保留 |

- 車輪のエンコーダはない（M-008）。**LiDAR と独立に車体の速度を測る手段は、今は GNSS の速度だけ**。
- GNSS の実車での状態: RTK fix と屋外での方位は、まだ確かめていない（第114便: 衛星の信号 0、NTRIP 0 バイト。DEC-139・DEC-144 の (c) が残っている）。
- 規則: 自前の GNSS 基地局による RTK は使ってよい（SR-04）。歩道の緑ロードコーンの車道側を走る区間がある（SR-15）。

## 2. 人混みで何が起きるか（推測。実データでは未確認）

| 起きること | 影響を受ける部分 | 仕組み |
|---|---|---|
| 地図にない点が大量に入る | NDT | 人・ロボットの点が地図の壁・柱と取り違えられ、照合が偏る（横にずれる、向きがずれる） |
| 地図の構造が隠れる | NDT | LiDAR（高さ約 1.18 m）の低い角度の光線が人で遮られ、遠くの建物・縁石が見えない。照合に使える点が減る |
| 動くものに引きずられる | GLIM の odometry | 周りの人が車体と同じ向きに歩くと、「周りが止まっている」前提が崩れ、速度を小さく見積もる |
| 特徴が少ない場所と重なる | NDT・GLIM | 開けた広場・まっすぐな歩道で、残った点だけでは前後の方向が決まらない（退化） |

逆に、**人混みでも影響を受けにくい手がかり**（推測）:
- 人の頭より高い所の構造（建物の 2 階以上の壁、街灯、標識、木の幹の上の方）。XT-32 の上向きの光線が当たる。
- 空（GNSS）。ただし建物の近く・木の下では RTK fix が落ちる。

## 3. 「GNSS＋IMU を主、LiDAR を補助」をそのまま採ると何が問題か

人の例示の案を、今の車体で検討した（数値は AI の計算と一般的な目安。実車では未確認）。

1. **GNSS は場所によって使えない**。RTK fix なら数 cm だが、float で数十 cm〜1 m、単独測位で数 m（ND-19 の記録で約 6.4 m）。ロードコーンで区切られた歩道では 1 m のずれでもはみ出す。市役所・研究学園駅の周りの建物、並木の下で fix がどれだけ続くかは未確認（DEC-293 で測る）。
2. **IMU だけでは位置を数秒しか保てない**。加速度の偏り b が残ると位置の誤差は ½·b·t²。b = 0.01 m/s²（約 1 mg）でも 10 秒で 0.5 m、30 秒で 4.5 m。傾きの誤差 0.1° は重力の漏れ込みで約 0.017 m/s² に当たる。TR-IMU16607 の実際の偏りは未測定。
3. **車輪のエンコーダがない**ので、GNSS が切れた間に IMU を支える速度がない。この車体で GNSS が切れたときに位置を保てるのは、結局 LiDAR（GLIM・NDT）だけ。

結論（AI の判断）: 「GNSS を主にする」かどうかを一つに決めるのではなく、**手がかりごとの品質で重みを変え、互いに見張らせる**のがよい。GNSS が fix の開けた場所では、結果として人の例示の「GNSS＋IMU が主」と同じ動きになり、建物の近く・並木の下では LiDAR が主になる。

## 4. 推奨する構成（案 a）

```
                         ┌───────────────── 品質で重みを変える・食い違いを見張る ─────────────────┐
GNSS（RTK、位置・方位）──┤ ・fix の種類・共分散・補正の経過時間で採否と重み                          │
NDT（人の頭より上の点）──┤ ・NDT のスコア・点の数で重み                                              ├→ map→odom（ND-07 だけが出す）
GLIM＋IMU（相対の動き）──┤ ・短い途切れ（GNSS も NDT も使えない数秒）をつなぐ                        │
                         └ ・GNSS と NDT が続けて食い違う → 推定不能（今の TR-07 の一時停止）────────┘
LiDAR の全点 ───────────→ 障害物（costmap。今のまま）
```

### 4.1 LiDAR の側の対策（安く効く見込み。DEC-291）

1. **NDT に入れる点を、人の頭より高い所に絞る**（高さの帯）。gouda_a3_points に「地面からの高さ h 以上の点だけを残す」設定を足す。事前地図の側は今のまま（全部の点）でよい（走行中の点の一部を、地図の全体と照合するのは NDT で普通の使い方）。
   - 目安の計算（AI。XT-32 の上側の視野 +15° は仕様の記憶で、原本未照合）: LiDAR の高さ 1.18 m から +15° の光線は、約 3.1 m 先で高さ 2.0 m を越える。h ≈ 2.0 m にすると、車体から約 3 m より遠い、頭より上の構造の点が残る。
   - 弱点: 頭より上の構造が少ない開けた場所では点が足りなくなる。h は実測で決める（DEC-293）。地面の高さは「車体の高さから一定」で近似する（坂では誤差。今の帯の地図と同じ考え方、localization_selection §1）。
   - 近くの点を捨てる距離（今の PRM-79）を、人が密集する距離まで広げるかも同じ評価で決める。
2. **事前地図をきれいにする**。地図作成は人の少ない時間に行う。地図に残った人・車の点を消す処理（動的物体の除去）を map_creator に入れるかは、評価で地図の汚れが問題になったときに改めて提案する（今は提案しない）。
3. **NDT の品質を重みにする**。NDT のスコア・使った点の数が悪いときは、捨てるか共分散を大きくして EKF に渡す。Autoware の NDT が出す品質の値を使う（しきい値は実測。DEC-286 の EKF のしきい値の件とまとめて扱う）。

### 4.2 GNSS を走行中の観測として使う（DEC-290。DEC-130 の T5 を採用する形）

- 前提（今の未決の項目のまま）: RTK fix と方位を屋外で確かめる（DEC-139、DEC-144 の (c)）。地図と GNSS の座標の対応（enu→map、DEC-131・135）。
- 採否の規則（値は tbd、DEC-293）: RTK fix のときだけ位置を使う。float・単独は使わない（または非常に大きな共分散）。方位は受信機が有効と出すときだけ。補正が一定時間届かなければ使わない。
- 突然の誤った fix（マルチパス）への備え: 今の推定からの距離（マハラノビス距離）が大きい観測は捨てる。捨てたことを記録する。
- 融合の方法は二つ（どちらにするかは実装の承認の時に。上流の確認がまだ）:
  - (i) 今の autoware_ekf_localizer に GNSS の姿勢も入れる。複数の姿勢の入力をどう扱うかは上流のソースで未確認（要確認）。
  - (ii) EKF を robot_localization（VM に 3.8.3 が入っている）に替える。複数の姿勢の入力と、入力ごとの棄却のしきい値を持つ。
- 融合は Nav2 の外の自己位置推定の中だけ。map→odom は ND-07 だけが出す（同じ TF を二つから出さない）。

### 4.3 食い違いの見張り（DEC-134 の T4。今の承認待ちのまま）

- GNSS（fix）と NDT が一定時間・一定距離以上食い違ったら、推定不能として今の TR-07（一時停止）に入る。どちらが正しいかを自動で決めて走り続けることはしない（案 a の範囲では）。
- 人混みの中で一時停止すること自体は、今の intent の振る舞いの範囲（推定不能で一時停止、再開は人のボタン）。

### 4.4 デバッグ性（intent の優先順位 1）

融合は切り替えより原因を追いにくい。次を記録する（今のログの方式に足す）:
- 入力ごとの値・品質・採否と、捨てた理由（GNSS の fix の種類、NDT のスコア、マハラノビス距離）
- GNSS と NDT の差、EKF の共分散
- 記録の再生で、融合の結果を再現できること（GNSS・NDT・GLIM の出力を rosbag に残す）

## 5. ほかの案

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|

| c | 今の NDT が主のまま、§4.1 の LiDAR の対策と §4.3 の見張りだけ | 変更が一番小さい。GNSS は見張りだけなので誤った fix で走りが変わらない | 人混みで NDT が実際に崩れると、一時停止が増えるだけで走り続けられない |
| d | 区間ごとに切り替え（waypoint の区間に「GNSS 主」「NDT 主」を人が付ける。Autoware の pose_estimator_arbiter に近い考え方） | 振る舞いが決まっていて追いやすい（デバッグ性） | 区間ごとの設定が人の作業になる。区間の境で跳ぶ。waypoint の契約を変える |

AI の推奨の順: **c をすぐ（LiDAR の対策は GNSS の準備を待たずにできる）→ 評価（DEC-293）→ a**。評価で「人混みの区間で NDT は崩れない」と分かれば c で止める。「崩れる区間が GNSS の fix が続く区間と重なる」なら a に進む。

## 6. ハードウェアの案（DEC-292）

- **車輪のエンコーダ**を足すと、LiDAR と GNSS の両方が弱いときに位置を保てる手段が増える（車輪の滑り・段差では誤差）。ESP32 の通信（esp32_protocol_v4）と local_odometry（M-008）の変更になる。
- 代わり: GNSS の速度（受信機の PVT の速度）を、GNSS が使える間の速度の観測として使う（ハードの変更なし）。
- AI の推奨: 評価（DEC-293）で「GNSS も NDT も弱い時間」が何秒続くかを見てから決める。ただしハードは準備に時間がかかるので、評価は早めに行う。

## 7. 評価の手順の案（DEC-293）

1. **記録を取る**（人の作業）: XT-32・IMU・GNSS（RTK）を同時に rosbag に記録する。
   - 本番のコースの区間で、人の多い時（休日、試走会）と少ない時に同じ区間を走る。
   - 人混みを作る試験: チームの人が車体の周りを歩く・並んで歩く（同じ向き、逆向き）。
2. **オフラインで比べる**（AI の作業。車体は動かさない）:
   - NDT（今の前処理）と NDT（高さの帯 h をいくつか）を同じ rosbag に通す。
   - 比べる量: NDT の位置と RTK fix の GNSS との差、0.5 m を超える跳ねの回数（localization_selection の残る課題 1）、NDT のスコア・点の数。
   - GNSS: コースに沿った RTK fix の割合と、fix が切れる場所・長さ。
   - GLIM の odometry の、人が同じ向きに歩く場面での速度の誤り。
3. これで決める値: 高さ h、近くの点を捨てる距離、NDT の品質のしきい値、GNSS の採否の規則、食い違いの判定（T4）の値。**証拠（rosbag、条件、解析のスクリプト、日付）がない値は確定にしない**。

## 9. 安全上の注意（CLAUDE.md 1.4・1.5）

- GNSS を融合しても、自己位置が正しいことの保証にはならない。誤った fix（マルチパス）、補正の古さで、もっともらしく間違うことがある。**GNSS の品質区分を安全の根拠にしない**。
- 「推定不能 → 一時停止」は、PC の出力を中立にするだけで、車体全体の停止の保証ではない（手動の優先、ESP32・駆動系の故障、慣性・斜面）。
- 高さの帯で人の点を捨てるのは**自己位置推定の入力だけ**。障害物（costmap）には全点を使う（今のまま）。混同しない。
- 人混みでは、自己位置推定とは別に、Nav2 が経路をふさがれて一時停止になる回数が増える見込み（blocked）。これは本書の範囲外（SR-08 の速度・距離の件と合わせて別に扱う）。
