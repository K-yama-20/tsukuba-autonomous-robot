## 1. 原則

1. **モードは 4 つのまま**（自律走行・事前地図作成・待機・手動走行。RQ-I065）。新しいモードは作らない。
2. **自律走行から自動で待機に入るのは、最後の waypoint への到達（TR-08）だけ**にする。ほかの異常・待ちは、**自律走行モードのまま、処理の段階（processing_state、DEC-010 の仕組み）**で表す。
3. **規則の一時停止（停止線・道路端）も、自律走行モードの中の段階**にする。待機には入れない。再開は人の操作（規則が失格の例外としている「一時停止から走行再開するための操作」）。
4. **人の操作は今のまま**：待機ボタン（TR-06）、自律走行終了ボタン（TR-11・12）、待機からの再開ボタン（TR-10）、ゲームパッドの手動操作（ESP32 で優先。基本契約）。人の操作の後は自動で走り出さない（基本契約）。
5. 自動の段階の移り変わりは、すべて原因・時刻・続いた時間をログと monitor に出す（デバッグ性）。待機に入らない代わりに、「いま何を待っているか」を見えるようにする。

## 2. 自律走行モードの中の段階（新設計）

今の `processing_state`（SoftwareMode.msg：「idle」「goal_sending」「cancel_waiting」「recovering」など、モードとは別の処理の段階）を、次の段階で使う。値の名前は案。

| 段階 | 入る条件 | している事 | 出る条件 | 関係する判断 |
|---|---|---|---|---|
| **走行中** `driving` | goal が受け付けられた | Nav2 が走る。motion_hold を解く（DEC-311） | 下の各条件 | DEC-311 |
| **停止線で待つ** `rule_stop_hold` | 区間の終わりの waypoint が `kind: stop` で、その区間の goal が成功した | motion_hold を出して止まる。時間の上限なし。monitor に「横断を始める」操作を出す | 人の「横断を始める」操作 → 次の区間の goal を出す → `driving` | DEC-332、DEC-343 |
| **推定の回復を待つ** `localization_wait` | ND-07 の状態が正常でない | 案は §3。ND-07 は推定を続ける | ND-07 が正常に戻った（連続 N 回、tbd）→ 現在地から残りの waypoint へ goal を出し直す → `driving` | DEC-306、DEC-340、DEC-342 |
| **経路を出し直す** `goal_retry` | Nav2 の goal が失敗で終わった。開始の手順が失敗した | 失敗を記録 → 旧 goal の終了を確かめる（intent.md 16 行の順序）→ 必要なら Nav2 を RESET → 現在地から残りの waypoint へ goal を出し直す。回数の上限なし（50 回ごとに理由を記録：G-RECOVERY-COUNT） | goal が受け付けられた → `driving` | DEC-307 |
| **滞留から抜ける** `stuck_escalation` | 最後に 1 m 進んでから T1 秒（tbd） | 段 1：costmap の消去と BT の recovery。段 2：inflation を小さくする（§5）。段 3 は §4 の制限つき | 1 m 進んだ → `driving`（段を戻す） | DEC-310、DEC-313、DEC-344 |
| **部品の復帰** `recovering` | node の異常・ドライバの終了・通信の途絶（TR-13） | motion_hold を出す → 必要な部品だけ作り直す（ドライバは DEC-308）→ 旧 goal の終了を確かめる → 必要なら推定の回復を待つ | 復帰した → `goal_retry` | DEC-308、TR-13 |

- 段階どうしが重なるとき（例：推定不能の間に Nav2 も失敗）は、優先の順を **recovering ＞ localization_wait ＞ rule_stop_hold ＞ goal_retry ＞ stuck_escalation ＞ driving** とする（案）。
- **待機に入る自動の契機は TR-08 だけ**。TR-07（Nav2 の失敗・推定不能 → 待機）と TR-09（自動復帰の不能・上限 → 待機）はなくす。
- 人が待機ボタンを押せば、どの段階からでも待機に入る（TR-06）。再開ボタンで自律走行に戻ると、段階は `goal_retry` から始まる（現在地から出し直す）。

## 3. 推定の回復を待つ（DEC-340 の具体化、DEC-342）

人の発言（DEC-340）：時間がたつと推定できるようになる可能性がある。案を 3 つ挙げる。

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| a. 走り続ける（DEC-306 の推奨） | map→odom を最後の値に保ち、GLIM の odometry だけで走り続ける | 止まらない。滞留にならない | 推定がずれたまま走ると経路を外れる。コースを大きく外れる・車道に入ると失敗（EV-15・16） |
| b. その場で止まって待つ | motion_hold を出して止まり、ND-07 の回復を待つ。回復したら自動で走り出す | ずれたまま進まない | 人混みが去るまで動けない。確認走行区間では 3 分で失敗。100 分の時間を使う |
| **c. 少し進んでから待つ（推奨）** | 推定不能になってからの距離が D（tbd）までは a で走り、D を超えたら b で止まって待つ。回復したら自動で走り出す | 一時的な推定不能（人に囲まれた数秒）では止まらない。長く続くときはずれが大きくなる前に止まる | D の値を実測で決める必要がある（GLIM の odometry のずれの実測） |

- どの案でも待機には入らない。ND-07 は推定を続け、推定不能の理由・続いた時間・進んだ距離を monitor とログに出す。
- 推定不能の判定の値（PRM-89〜93）は、待機に入るしきい値から「段階に入るしきい値」に意味が変わる（DEC-286 も同じ）。
- 回復の判定に連続 N 回（tbd）を置いて、正常と異常の行き来で走る・止まるを繰り返さないようにする。
- 将来：人の方針（DEC-325）の「GNSS・IMU で経路に追従」は、c の D を延ばす手段になる（今は GNSS が衛星を追尾していない：第129便）。

## 4. 横断歩道・道路端の一時停止（DEC-332 の具体化、DEC-343）

**仕組み（案）**
- waypoint の `kind` はすでに `pass`／`stop` を持つ（`waypoints.py:43`。今は記録だけで振る舞いに使っていない）。`kind: stop` を「規則の一時停止の位置」として使う。waypoint のデータの形は変えない。
- 今は NavigateThroughPoses の goal 1 つに残りの waypoint を全部入れている（`autonomy_client.py:272-289`）。これを、**次の `stop` の waypoint までの区切りごとに goal を出す**形に変える。区切りの終わりの waypoint で Nav2 が止まる（goal の成功）。
- goal が成功し、その終わりが `stop` なら `rule_stop_hold` に入る。motion_hold を出し、monitor に「横断を始める」操作を出す。人がそれを押したら、次の区切りの goal を出す。
- 最後の waypoint に着いたら、今のまま待機（TR-08）。

**決めること（DEC-343）**
1. 「横断を始める」操作のボタン：待機からの再開ボタン（TR-10）と同じボタンを、段階によって意味を変えて使うか、別のボタンにするか。推奨は**別のボタン**（押し間違いで待機の再開と取り違えない。ログの区分が明確）。
2. 止まる位置の精度：区切りの終わりは Nav2 の goal の判定（上流の既定で xy 0.25 m・向き 0.25 rad、雛形の値）で止まる。規則の「指定された領域」に入るかは未確認（DEC-346 で実測）。
3. 止まっている間に後ろから人・ロボットが来ても動かない（時間の上限なし）。

**変えないもの**：信号の判断は人がする（EV-23。Gouda は信号を見ない）。

## 5. 場所ごとの inflation（人の問いへの答えと、DEC-344）

人の問い「inflationの範囲を場所毎に異なる値に設定することは可能か？」への答え：**可能**（確認した事実）。
- 上流 Nav2 1.3.13 の InflationLayer は、`inflation_radius`・`cost_scaling_factor` を走行中に変えられる（`inflation_layer.cpp` の dynamicParametersCallback、449 行）。
- 方法 1（推奨）：waypoint の区間の属性に inflation を足し（速度の上限と同じ扱い。Gouda は今の区間を `current_section` で追っている）、区間が変わったら mode_manager が parameter を変える。確認走行区間（コーン）では大きく（狭い隙間を通れないとみなして迂回させる、DEC-339 の人の方針）、狭い歩道では小さくする。
- 方法 2：上流の BinaryFilter（`costmap_filters/binary_filter.cpp`、1.3.13 にある）でマスクの中にいるかを topic で出し、それを見て parameter を変える。地図の上の範囲で決められるが、部品が増える。
- 注意：local と global の両方の inflation を変える。変えた瞬間に経路が変わる（引き直し）。値は実測で決める（DEC-314）。

**滞留から抜ける段階の制限（DEC-344）**：別のセッションの DEC-310 の段 3（今の waypoint を飛ばして次へ）は、`stop` の waypoint を飛ばすと停止線で止まれず失敗（EV-22）、角の waypoint を飛ばすとコースを外れる恐れがある。推奨は、**`stop` の waypoint は飛ばさない**、段 3 は確認走行区間の外だけ、とする。

## 6. 起動・PC の再起動（DEC-309 との関係）

- PC の再起動の後、直前が自律走行で人の待機・終了の操作の後でなければ、自律走行に戻る（intent.md 第16版 94 行）。初期姿勢は最後に記録した推定の姿勢。
- 戻った直後は `localization_wait` から始める（推定が正常になるまで動かない。§3 の b）。推定の回復を待つ仕組みをそのまま使えるので、別の手順は要らない。
- 直前が `rule_stop_hold` だった場合は `rule_stop_hold` に戻る（人の操作を待つ）。勝手に横断を始めない。

## 10. 重大な要求・危険・前提（CLAUDE.md 1.4）

- 自動で待機に入らないので、異常の間も車体は自律走行モードのまま。止める手段は人の待機ボタン・終了ボタン・ゲームパッド。ゲームパッドはスタートの後に使うと失敗（EV-19）。待機ボタンが規則上許されるかは未確認（DEC-345）。
- 案 c では、推定がずれたまま D まで走る。コースを外れる・車道に入ると失敗。
- `rule_stop_hold` は時間の上限なしで止まる。人が押し忘れると、確認走行区間では 3 分で失敗。
- 停止線で止まる位置の精度は未確認（DEC-346）。
- PC の出力の中立化は、車体全体の停止の保証ではない（CLAUDE.md 1.5）。ESP32 の watchdog（PRM-13）は一定時間の未受信しか検出しない。
- 「実車投入可能」は人の判断待ち。
