# Nav2 の後退の速度の上限の検討（2026-10-21、第91便、DEC-198 の判断の材料）

人の指示（原文）：「それぞれの実装のメリデメを詳細に検討せよ。特に、回転と後退が組み合わさった機動をする際の境界条件について考えよ」

人の説明（原文、DEC-197）：「後退の速度上限が前進速度上限よりも遅いのは、車椅子側の内部制御のせいである。また、100%倒したときに後退速度上限に当たってしまうと考えよ。つまり、倒し量-速度のグラフの傾きが小さくなったと考えよ。」

読んだコミット: `34bc9e0` ＋ 作業ツリー（REV-122・123 を適用した後）。調査と計算だけで、コードは変えていない。

## 1. 比べる案

| 案 | 内容 | 変えるもの |
|---|---|---|
| A | Nav2 の velocity_smoother の後退の上限（min_velocity の x）を PRM-78（0.472 m/s）にする | `gouda_core/gouda_core/nav2_config.py` の 1 か所と、その試験 |
| B | 今のまま。後退の上限は前進と同じ PRM-66（1.25 m/s） | なし |
| C（参考） | motion_controller で、倒し量が ±1 を超えるとき、前後と旋回を同じ割合で縮める（軸ごとの頭打ちをやめる）。A・B と組み合わせられる | `motion_core.py` |

## 2. 指令が車体に届くまで（事実、コードで確認）

1. Nav2：経路の追従（RPP）、recovery の BackUp・Spin が cmd_vel_nav を出す。velocity_smoother が速度・加速度の上限を掛けて cmd_vel（IFD-15）を出す（`gouda_core/launch/gouda_nav2.launch.py:43-50`）。
2. motion_controller（`motion_core.py`）：前後の倒し量は、linear.x が 0 以上なら ÷1.25（PRM-39）、負なら ÷0.472（PRM-78）。旋回の倒し量は angular.z÷0.97（PRM-40）。それぞれを **軸ごとに** [−1, 1] で頭打ちにする。
3. 不感帯の補償（DEC-171、設定されたとき）：軸ごとに、最低倒し量＋(1−最低倒し量)×r。
4. vehicle_bridge：x＝−旋回、y＝前後。
5. ESP32 の mapVoltage（`firmware/gouda_esp32_v4/include/gouda_v4/control.hpp:31-46`）：倒し量のベクトルの大きさが 1 を超えると、向きを保ったまま **半径 1 の円の上** に縮める（前後と旋回が同じ割合で小さくなる）。中立 2500 mV、端は ±2220 mV で上下左右が同じ（円の中心は中立）。
6. EMC-270：倒し量を左右の車輪の速度に変える。後退の側は傾きが小さい（DEC-197）。**旋回の成分が後退のときにどう変わるかは未確認。**

## 3. 今の Nav2 の設定で、後退と回転はどこから出るか（事実）

- 経路の追従（RPP）は `allow_reversing: False`（`nav2_config.py:97`、DEC-122）なので、後退の指令を出さない。
- recovery の BackUp は、上流の BT のまま `backup_dist="0.30" backup_speed="0.15"`（真っすぐ 0.30 m を 0.15 m/s で後退。回転なし）。
- recovery の Spin は `spin_dist="1.57"`（その場の回転。前後の速度なし）。速さの上限は behavior_server の max_rotational_vel＝1.0（PRM-67）。
- velocity_smoother の後退の上限は −1.25 m/s（`nav2_config.py:128`。前進と同じ値を負にしたもの）。

**したがって今は、Nav2 が 0.472 m/s を超える後退を指令することはなく、案 A と案 B で車体の動きは同じ。** 後退と回転が同時に出るのは、velocity_smoother が BackUp から Spin（または前進）へ速度をなだらかにつなぐ間だけで、後退の速さは 0.15 m/s 以下（推測：つなぐ時間は約 0.13 s、後退 0.15 m/s を減速 1.2 m/s² で 0 にする間）。

案 A と B の差が実際に出るのは、次のような変更をしたとき：BackUp の backup_speed を 0.472 m/s より大きくする（人の「recoveryの後退は自由に使って良い。」）、RPP の allow_reversing を true にする、後退する controller（MPPI など）に替える。

## 4. 回転と後退を組み合わせたときの境界の条件

以下の数は、EMC-270 が前後と旋回をそれぞれ直線で速度に変えると仮定した計算（実測ではない）。

### 4.1 倒し量の円（ESP32）による境界

車体が出せる (v, ω) の範囲は、四角（軸ごとの上限）ではなく楕円になる。

- 前進側：(v／1.25)² ＋ (ω／0.97)² ≦ 1
- 後退側：(v／0.472)² ＋ (ω／0.97)² ≦ 1（後退は傾きが小さいので、同じ速さでも倒し量が大きく、円の縁に早く当たる）

| 一緒に出す回転 ω | 出せる前進の速さ | 出せる後退の速さ |
|---|---|---|
| 0.3 rad/s | 1.189 m/s | 0.449 m/s |
| 0.5 rad/s | 1.071 m/s | 0.404 m/s |
| 0.8 rad/s | 0.707 m/s | 0.267 m/s |

Nav2 の上限は軸ごと（四角）なので、この楕円を知らない。楕円の外の指令は、ESP32 が円に縮める。このとき前後と旋回は同じ割合で小さくなり、**曲がる半径（v／ω）は保たれ、速さだけが落ちる**。案 A・B のどちらでも同じ。

### 4.2 軸ごとの頭打ちによる境界（曲がる半径がずれる）

前後か旋回の一方だけが頭打ちになると、v／ω の比が変わり、**指令より小さい半径で曲がる**。

| 指令 (v, ω) | 案 B：倒し量 | 円に縮めた後 | 実際 (v, ω)（仮定） | 半径 指令→実際 |
|---|---|---|---|---|
| (−0.15, 0)（BackUp） | (−0.318, 0) | 同じ | (−0.150, 0) | 直進 |
| (−0.10, 0.5)（つなぎ目） | (−0.212, 0.515) | 同じ（大きさ 0.557） | (−0.100, 0.500) | 0.20→0.20 m |
| (−0.40, 0.8) | (−0.847, 0.825) | 大きさ 1.183→(−0.717, 0.697) | (−0.338, 0.677) | 0.50→0.50 m |
| (−0.80, 0.8) | (−1.000, 0.825)（後退が頭打ち） | 大きさ 1.296→(−0.771, 0.636) | (−0.364, 0.617) | **1.00→0.59 m** |

- 最後の行は、今の設定では出ない指令（後退 0.8 m/s）。
- 案 A でも、velocity_smoother が軸ごとに頭打ちにするなら（推測：smoother の上限は軸ごと。上流のソースは読んでいない）、v は −0.472 になり、ω は 0.8 のまま残る。その結果、倒し量は案 B と同じ (−1.000, 0.825) になり、半径のずれも同じ。**つまり案 A は、曲がる半径のずれを直さない。** 直すのは案 C（同じ割合で縮める）：(−1.695, 0.825)→(−1.000, 0.487)→円で (−0.899, 0.438)→実際 (−0.425, 0.425)、半径 1.00 m を保つ。
- PRM-67（1.0 rad/s）は PRM-40（0.97 rad/s）を少し超える。前進でも旋回が頭打ちになると、同じ種類のずれが出る（DEC-192 の注）。

### 4.3 後退のときの減速の遅れ（案 B だけ）

- velocity_smoother は OPEN_LOOP（上流の雛形のまま）で、自分が最後に出した値を今の速度とみなす。
- 案 B で −1.25 m/s まで後退の指令が出たとすると、止めるとき smoother は −1.25 から 1.2 m/s² で減速する。しかし車体は、指令が −0.472 を下回るまで倒し切りのまま。**約 0.65 s（(1.25−0.472)／1.2）、減速が始まらない**。止まる位置が Nav2 の見込みより遠くなり、後退から前進への切り替えも同じだけ遅れる。
- 案 A では、smoother の値が −0.472 を超えないので、この遅れはない。

### 4.4 前後 0 の近く（その場の回転）と、後退のときの旋回

- v がほぼ 0 で ω だけがある（Spin、RPP のその場の回転）とき、正規化は v の正負で傾きが変わる（÷1.25 と ÷0.472）。値は 0 で連続していて、跳ねない。
- 不感帯の補償を設定すると、前進と後退の最低倒し量が違うので、v の符号が変わる所で出力が段差状に変わりうる。ただし、しきい値より小さい倒し量は中立にするので、v のわずかな揺れで前後が入れ替わることはない（しきい値を 0 にしない限り）。
- **未確認（実測が要る）**：
  - (a) EMC-270 が、後退の側で旋回の成分にも小さい傾きを掛けるか。掛けるなら、後退中の回転は motion_controller の想定（÷0.97）より遅くなり、曲がる半径が大きくなる。
  - (b) 後退のとき、同じ左右の倒し量で回る向きが前進と同じか（車椅子によっては後退で向きを反転する）。反転するなら、後退しながら回る指令は逆に曲がる。
  - (c) 前後 0 の線をまたぐとき、旋回の速さが跳ねないか。

  (a)〜(c) は、Nav2 の後退が 0.15 m/s 以下の今は影響が小さいが、後退を速くする前に確かめる必要がある。

### 4.5 安全の面（推測を含む）

- footprint は前が長い（前 0.55 m、後 0.24 m）。後退しながら回ると、前の角は大きな円を描く。指令より小さい半径で曲がると（4.2 の最後の行）、計画より前の角が外に振れる。Nav2 の衝突の判断は、指令した軌跡に基づく。
- PC の出力の中立化は車体の停止を保証しない（CLAUDE.md 1.5）。どの案でも、手動の優先と PC 指令の途絶時の中立化は ESP32 が受け持つ。

## 5. 利点と欠点

| | 案 A（0.472 m/s） | 案 B（今のまま） | 案 C（同じ割合で縮める） |
|---|---|---|---|
| 今の設定での車体の動き | 同じ | 同じ | 同じ（今は頭打ちが起きない） |
| 後退を速くしたときの減速・切り替えの遅れ | なし | 最大約 0.65 s | B と組み合わせると遅れは残る |
| 曲がる半径のずれ（軸の頭打ち） | 直さない | ある | 直す |
| 記録（rosbag の cmd_vel）と実際の速さ | 一致する | 0.472 を超える後退は実際と違う | 変わらない |
| コードの変更 | nav2_config の 1 か所と試験 | なし | motion_core と試験。RQ-I020（cmd_vel の後段で速度を抑えない）の例外を増やすので、承認が要る |
| 依存する値 | PRM-78（人の申告、実測していない） | — | PRM-39・40・78 |

## 6. 推奨

- **案 A を推奨する（予防）。** 今は動きが同じなので急がない。ただし、recovery の後退を速くする前に入れておくと、4.3 の遅れを防げて、記録と実際も一致する。
- 案 C は、曲がる半径を保ちたいときの別の案。RQ-I020 の扱いが絡むので、別に判断していただく。
- 後退を速くする前に、4.4 の (a)〜(c) を卓上か実車で確かめる（VL-02・DEC-050 と同じ機会でよい）。後で検証する項目（VL-03）にすることを提案する。

## 7. 確かめていないこと

- EMC-270 の倒し量と速度の関係（前後・旋回とも直線と仮定した）、後退のときの旋回（4.4 の (a)〜(c)）。
- velocity_smoother の上限が軸ごとか（上流のソースは読んでいない）。
- RPP の上流の既定値（その場の回転の条件など）。nav2_config は 4 つの値だけを上書きし、残りは RPP の既定値。

## 8. 決定（第92便で追記）

- 人の決定（原文、DEC-198）：「DEC-198 は案 A。nav2_config で velocity_smoother の後退の上限を PRM-78 にする実装を許可する。」
